# backlog — 人間判断待ち事項 / 自動判断の記録

このファイルは research-cycle が「本来は人間の判断が要るが，サイクルを止めないために暫定で自動選択した事項」と，
「不可逆・危険なため停止して人間に委ねた事項」を記録する．新しいものを常に先頭に追記する（逆時系列）．

書式:
```
## B{n} [auto-decided YYYY-MM-DD] 題目
- 状況: なぜ判断が要ったか
- 自動選択: 何を選んだか
- 根拠: なぜそれが最も妥当か
- 要レビュー: 人間が確認・却下する際に何を見るか（却下時はこの項目を編集して差し替える）
```
不可逆な事項は `[needs-human YYYY-MM-DD]` として記録し，Slack で @mention 済みであることを明記する．
人間が答えたら（herdr 上でも，Slack のスレッドへの返信（`[Slack 返信]`）でも），`[human-decided YYYY-MM-DD]` として
回答の内容と，それに従って何をしたかを追記する．

## B3 [auto-decided 2026-10-06] 回答の生成を貪欲な復号（temperature 0）にする
- 状況: RAGRoute は生成の温度を指定しておらず，Ollama の既定（0.8）で回答がばらつく．同じ質問への方式間の
  正答の違いを McNemar 検定で比べると，ばらつきが雑音として混ざる．
- 自動選択: `llm.temperature: 0.0`．あわせて質問者の Ollama を 2 件同時に処理させる
  （`llm.requester_num_parallel: 2`．実測で 1 回の生成は約 7.4 秒．1 件ずつだと MIRAGE の全問に約 16 時間）．
- 根拠: 選択式の評価では貪欲な復号が一般的で，対応ありの比較の検出力が上がる．
- 要レビュー: RAGRoute の論文値との正答率の比較では，温度の違いが差の原因の候補になる．

## B2 [auto-decided 2026-10-06] MedCPT の埋め込みを fp16 の混合精度で計算する
- 状況: 11 枚の GPU で分担しても，fp32 では PubMed の埋め込みが 1 枚あたり約 95〜190 断片/秒で，
  約 5,400 万断片に 13 時間以上かかる見込みだった．ユーザーが寝ている間に準備を終える必要があった．
- 自動選択: `data.medrag.embed_precision: fp16_autocast`（torch.autocast）で文書とクエリの両方を埋め込む．
  fp32 で作りかけていた 6 ファイルの埋め込みは消し，全ファイルを同じ条件で作り直した．
- 根拠: gpu2 の RTX 3090 で Textbooks の 7,070 断片と MIRAGE の 500 問を測った．fp32 の 2.6 倍速く
  （193 → 502 断片/秒），fp32 との差は最大 0.0017（値の大きさ約 6.5），上位 50 件の一致率 99.7%，
  上位 15 件の集合が一致した質問は 97% だった．関連ラベルも実機の検索も同じ埋め込みから計算するので，
  内部の整合性は保たれる．
- 要レビュー: MedRAG の fp32 の埋め込みとの厳密な一致を要する比較（例：RAGRoute の論文値との細かな比較）で
  差の原因の候補になる．fp32 に戻すなら `embed_precision: fp32` にして，埋め込み・ラベル・ルーターを作り直す
  （GPU 11 枚で 13 時間前後）．

## B1 [auto-decided 2026-10-06] 専門家ノード（13.x・14.x）が全台応答しない／hugepages の扱い
- 結論（00:50 追記）: 00:46 にネットワークが復旧した．13.x・14.x は再起動しておらず（uptime は 2 週間以上のまま），
  hugepages も 0 のままだった．止まっていたのはネットワーク（研究室のゲートウェイ）であり，hugepages の解放は
  原因ではないと判断して，`cluster.release_hugepages: true` に戻した．同じ時間帯に失敗したデータ準備の取得は，
  gpu2 で取得したデータを制御点へ送って補い，データ準備をやり直した．
- 要レビュー（結論について）: 研究室のゲートウェイが 00:33〜00:46 ごろに止まった理由（夜間の保守など）．
  再び止まると，制御点と wafl500〜509 はインターネットに出られなくなる（データ準備の取得とモデルの取得が失敗する）．
- 状況: 専門家ノード 20 台（192.168.13.100〜109，192.168.14.100〜109）では起動時の設定で 1 GB × 13 の
  hugepages が予約され（すべて未使用），通常のメモリが約 1.7 GB しか残っていなかった．MedRAG の 6 GB の索引も
  E0 の 8B モデルも載らない．ユーザーの許可を得て 2026-10-06 00:25 ごろに全台で `sysctl vm.nr_hugepages=0`
  を実行し，使えるメモリは 14 GB になった．その後 00:30 ごろに E0 の deploy（13.100・13.101 へのイメージの
  取得）を始めたところ，00:33 までに 20 台すべてが応答しなくなった（ping も SSH も不可）．deploy していない
  13.102・14.100 も同じである．ゲートウェイの 192.168.13.1・14.1 も応答しないが，以前から応答していたかは未確認．
  制御点（192.168.15.10）と wafl500〜509（192.168.15.x）は正常である．
- 追加の観察（00:37）: 制御点の既定ゲートウェイ 192.168.11.1 も応答せず，制御点からインターネット
  （huggingface.co・pypi.org・google.com）にも出られない．gpu2 からは出られる．研究室のネットワーク機器の
  障害とみるのが自然で，hugepages の解放が原因である可能性は低い（ホストの設定変更でゲートウェイは止まらない）．
  復旧後に 13.x・14.x の uptime を確かめ，再起動していなければホストは無事だったとみなして解放を有効に戻す．
- 自動選択: deploy が hugepages を解放する処理を `cluster.release_hugepages`（既定 false）で無効にした．
  ノードの電源やネットワーク機器の操作はできないので，復旧は人間に委ねる．
- 根拠: 解放と停止の因果は不明だが，解放の数分後に全台が止まっており，自律的に回るサイクルが同じ操作を
  繰り返すと被害が広がるおそれがある．
- 要レビュー: (1) 20 台が止まった原因（電源・スイッチ・夜間の自動停止・hugepages の解放のいずれか）．
  (2) 復旧後，hugepages を解放してよいなら `config.yaml` の `cluster.release_hugepages: true` にする
  （解放しないと MedRAG の deploy は OOM で失敗する）．恒久的には起動時の `hugepages=6` の設定を外すのが確実．
  (3) 復旧するまで，13.x・14.x を使う E0・E1 は実行できない．データ準備（wafl500〜509 と制御点）は影響を受けない．
