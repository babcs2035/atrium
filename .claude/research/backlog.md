# backlog — 人間判断待ち事項 / 自動判断の記録

このファイルは research-cycle が「本来は人間の判断が要るが，サイクルを止めないために暫定で自動選択した事項」と，
「不可逆・危険なため停止して人間に委ねた事項」を記録する．新しいものを常に先頭に追記する（逆時系列）．

書式:
```
## B{n} [auto-decided YYYY-MM-DD] 題目
- 状況: なぜ判断が要ったか
- 自動選択: 何を選んだか
- 根拠: なぜそれが最も妥当か
- 要レビュー: 人間が確認・却下する際に何を見るか（却下時はこの項目を編集して差し替える）
```
不可逆な事項は `[needs-human YYYY-MM-DD]` として記録し，Slack で @mention 済みであることを明記する．
人間が答えたら（herdr 上でも，Slack のスレッドへの返信（`[Slack 返信]`）でも），`[human-decided YYYY-MM-DD]` として
回答の内容と，それに従って何をしたかを追記する．

## B1 [needs-human 2026-10-06] 専門家ノード（13.x・14.x）が全台応答しない／hugepages の扱い
- 状況: 専門家ノード 20 台（192.168.13.100〜109，192.168.14.100〜109）では起動時の設定で 1 GB × 13 の
  hugepages が予約され（すべて未使用），通常のメモリが約 1.7 GB しか残っていなかった．MedRAG の 6 GB の索引も
  E0 の 8B モデルも載らない．ユーザーの許可を得て 2026-10-06 00:25 ごろに全台で `sysctl vm.nr_hugepages=0`
  を実行し，使えるメモリは 14 GB になった．その後 00:30 ごろに E0 の deploy（13.100・13.101 へのイメージの
  取得）を始めたところ，00:33 までに 20 台すべてが応答しなくなった（ping も SSH も不可）．deploy していない
  13.102・14.100 も同じである．ゲートウェイの 192.168.13.1・14.1 も応答しないが，以前から応答していたかは未確認．
  制御点（192.168.15.10）と wafl500〜509（192.168.15.x）は正常である．
- 自動選択: deploy が hugepages を解放する処理を `cluster.release_hugepages`（既定 false）で無効にした．
  ノードの電源やネットワーク機器の操作はできないので，復旧は人間に委ねる．
- 根拠: 解放と停止の因果は不明だが，解放の数分後に全台が止まっており，自律的に回るサイクルが同じ操作を
  繰り返すと被害が広がるおそれがある．
- 要レビュー: (1) 20 台が止まった原因（電源・スイッチ・夜間の自動停止・hugepages の解放のいずれか）．
  (2) 復旧後，hugepages を解放してよいなら `config.yaml` の `cluster.release_hugepages: true` にする
  （解放しないと MedRAG の deploy は OOM で失敗する）．恒久的には起動時の `hugepages=6` の設定を外すのが確実．
  (3) 復旧するまで，13.x・14.x を使う E0・E1 は実行できない．データ準備（wafl500〜509 と制御点）は影響を受けない．
