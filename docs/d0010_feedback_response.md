## A. プライバシーの防御と脅威モデル

### d0010 A1. 脅威モデルの明文化（文書．優先度：高）

- コメント：「どのような機密性を保証するのか」「悪意ある質問者の繰り返しの質問を想定しているか」「暗号技術で精度を保てるか」．
- 作業：`docs/d0001_architecture.md` に「脅威モデル」の節を追記し，報告書の第 7 章（`docs/d0008` §7.4）にも同じ内容を入れる．次を表にする．
  - 守る対象：各受信箱のメール本文．公開情報（要約）と質問の内容も露出の対象として数える．
  - 主体：質問者，受信箱の持ち主の PC，生成を委託される GPU の PC，中央（参照点）．
  - 想定する相手：組織内の「正直だが好奇心のある」参加者（決められた手順は守るが，受け取った情報は見る）．
  - 測るが防がない相手：多数の質問を投げて中身を集める質問者（d0010 A3 で量だけ測る）．
  - 想定しない相手：ノードの改ざん，偽の公開情報（ルーティングの乗っ取りの攻撃の研究がある），通信路の盗聴（d0010 F2 で暗号化の費用だけ測る），判定モデル・生成モデルの侵害．
  - 保証しないこと：暗号的な機密性，差分プライバシー（d0010 A2 で公開情報にだけ付ける場合は，その範囲を明記する）．
  - 本研究の目標：データを持ち主の手元に置くという制約（法令・組織の都合）を守ったうえで，外に出る量を測り，減らすこと．
- 暗号技術についての記述：機密計算（C-FedRAG），秘密分散・準同型暗号を使った検索，差分プライバシーの合成データ（DP-SynRAG）などの文献を挙げ，精度・費用の兼ね合いを文献の範囲で述べる．実装は範囲外とする．
- 判定：なし（文書）．journal に「文書の項目」として記録する．
- 費用：半日．

### d0010 A2. 公開情報への差分プライバシーのノイズとマスク（オフライン＋オフラインの再生．優先度：高）

- コメント：「マスクやノイズで防御したとき正答率はどうなるか」「差分プライバシーの研究はどこまで進んでいるか」「精度を保ちながらどこまで隠せるか」．
- 背景：主構成の 1 段目（`bm25_probe` の候補の選び方）は，各デバイスが公開する語の統計（BM25 の文書頻度．上位 64,000 語）を使う．公開情報から持ち主を 72.6% 特定できる（hybrid の要約）．
- 防御の候補（事前登録で 2〜3 個に絞る）：
  1. **文書頻度へのラプラス雑音**：語ごとの文書頻度に雑音を加える．1 通のメールの追加・削除で各語の文書頻度は最大 1 変わるので，公開する語の数を V としたときの感度で ε を割り当てる（語の選び方そのものも漏れるので，公開する語彙を全デバイス共通の固定の語彙にするか，差分プライバシー付きの上位 k の選択を使う）．
  2. **重心へのガウス雑音**：埋め込みの重心を使う構成（hybrid の重心の部分）では，各メールの埋め込みのノルムを C に切り詰めたうえで雑音を加える．
  3. **マスク**（差分プライバシーの保証なし）：受信箱の中の文書頻度が k 未満の語（その受信箱に固有の語．名前などを含みやすい）を公開しない．メール特有の規則（名前の辞書など）は使わない（汎用性の原則）．
- 振るもの：ε ∈ {∞, 8, 4, 2, 1, 0.5}（雑音），k ∈ {1, 2, 5, 10}（マスク）．
- 測るもの：
  - 持ち主の特定（公開情報から，あるメールの持ち主を当てる率．top-1・AUC．ヘッダーを除いた本文の入力を主にする．`owner-eval` の定義）．
  - 見つけやすさ（持ち主が候補 3 つに入る割合 hit@3）．
  - 要求数（候補の数は固定なので変わらない．記録だけ）．
  - 正答率：hit@3 が変わる問だけ，候補を作り直して V2 の正答率をオフラインの再生で測る（d0009 Iteration 41・42 と同じ方式．wafl500〜509）．
- 段階：(1) dev と H でオフラインの曲線（hit@3 と持ち主の特定）を出す（記述）．(2) 主構成に入れる設定を選ぶなら dev で選び，H4 で判定する（運用ルール 10）．
- 判定の骨子：「持ち主の特定の top-1 を半分以下にしたときの，正答率の低下」を主の数値にする．採否を決めるなら，dev で「正答率の低下 ≤ 0.01 で持ち主の特定が最も下がる設定」を選び，H4 で非劣性（δ = 0.02）を判定する．
- 注意：差分プライバシーの保証は**公開情報についてだけ**で，質問者・委託先へ渡る文書や回答には及ばない．このことを結果の全ての記述に添える．
- 費用：オフラインの曲線は 1 日，再生は 1〜2 日．

### d0010 A3. 繰り返しの質問による抽出（実機の retrieval_only．優先度：中）

- コメント：「悪意ある質問者が繰り返し質問した場合は」．
- 方法：正規の質問者が質問の予算 N を持つとする．攻撃の質問の作り方は 2 通り（事前登録で決める）．
  - (i) EnronQA の train の質問を無作為に使う（ふつうの利用者を装う）．
  - (ii) query-based sampling：受け取った文書から語を取り出して次の質問を作り，取り出す文書を増やす．
- 測るもの：質問の数 N に対して，質問者が受け取った重複なしの文書（全体と受信箱ごと）の割合．主構成（1 問 15 通が渡る）と，回答だけを返す構成（参考）で比べる．中央は「中央の 1 台が侵害されれば全 73,772 通」を比較の線として引く．
- 対策の評価：質問者ごとの質問の数の上限，受信箱ごとに 1 人の質問者へ渡す文書の上限（例：1 日あたり M 通）を入れたときの，抽出の割合と正答率．
- 実機：retrieval_only で生成は流さない（運用ルール 13 の「新しい測定は実機」に合わせる）．文書の受け渡しだけを数える．
- 費用：2〜3 日．
- 倫理：攻撃は自分たちのクラスタと公開データの中に限る．

## B. 「わからない」と評価

### d0010 B1. 作り話を罰する採点（CRAG 式）での比較（再採点．優先度：高）

- コメント：「『わからない』を禁じると精度は上がるが，でっち上げの害が増えるのでは」「0/1 を超える評価」．
- 背景：RAG のベンチマーク CRAG は，正解 +1，「わからない」0，誤答 −1 で採点し，作り話を「わからない」より重く罰する．d0009 A2 の 3 分類の結果があるので，この採点はほぼ再集計で出せる．
- 作業：
  1. P2P：A5（UNKNOWN を許す）と A6（通常）の test の 3 分類（d0009 A2）から，信頼性の得点（正解の割合 − 誤答の割合）を出す（記述）．
  2. P2P の主構成（V2．Iteration 41・42 の両腕）と，中央 C1-RRF-CE（H の 3 回の実行 `d0009_a3_c{1,2,3}`）を，`abstain-judge` で 3 分類し，同じ得点を出す（記述）．中央の 3 分類はまだ無いので採点の追加が要る（wafl500〜509）．
  3. 正答率の順位と信頼性の得点の順位が入れ替わるかを書く．
- 判定：なし（記述）．構成を選ばない．
- 注意：判定モデルは短い断定の答えを「わからない」にする誤りがある（d0009 A2）．人手での確かめの件数を事前登録で決める．
- 費用：1 日．

### d0010 B2. 「答えが文脈にあるか」の判定を，選択と棄権に使う（オフラインの再生．優先度：中）

- コメント：「持ち主以外の受信箱の『わからない』は選択の良い手がかりになるのでは」．
- 背景：A1 の `abstain` は，生成のプロンプトで「わからない」を許したので，持ち主の回答まで下げた（A6 で外して +0.0248）．V2 は「文脈が回答を支えるか」を別の LLM で問う．
- 方法：生成のプロンプトは通常のまま（持ち主の回答を下げない）．候補ごとに，生成とは別の 1 回の呼び出しで「この 5 通に質問の答えが書かれているか（はい／いいえ）」を問い，その確率を (a) V2 の特徴量に足す，(b) 全候補で「いいえ」が強いときに最終回答を「わからない」にする（棄権）．
- 評価：正答率と B1 の信頼性の得点の両方．棄権の閾値は dev で信頼性の得点が最大になる値に決め，H4 で判定する．
- 判定の骨子：(a) は正答率の改善（d0009 B3 と同じゲート：dev の増分 +0.006 以上で H4 へ），(b) は信頼性の得点の改善と，正答率の低下が δ 以内であること．
- 費用：2〜3 日（wafl500〜509 で判定の呼び出し）．

### d0010 B3. 確信度の較正（再集計．優先度：低）

- コメント：「agent の confidence や部分点など 0/1 以上の評価」．
- 作業：V2 の選択の得点（または B2 の確率）を確信度とし，正誤との較正（信頼性図・ECE）を H で記述する．部分点は CRAG の「acceptable」（0.5）を判定モデルの 4 分類で出せるかを試す（判定の追加が要る）．
- 費用：半日〜1 日．

## D. 規模・負荷・ネットワーク

### d0010 D1. 台数の拡大（実機．優先度：中）

- コメント：「分散配置する PC の台数を増減させたら，持ち主の発見率・正答率・遅延は」．
- 方法：1 台の専門家の PC で複数のノードのプロセスを動かし，論理的なデバイスの数を 30 → 60 → 150（1 受信箱 ＝ 1 デバイス）に増やす．減らす側は 30 → 15（2 台分の受信箱を 1 台にまとめる）．追加だけの設定キー（例：`cluster.nodes_per_host`）で表す．
- 測るもの：hit@3，要求数，待ち時間（p50・p95），処理量（retrieval_only を主に，生成まで含めるのは 1 点だけ），正答率（生成まで流す 1 点で）．
- 注意：同じ PC の CPU を共有する模擬で，台数が本当に増えた場合より遅く出る．各ホストの CPU 使用率を記録し，結果の読み方に添える．
- 費用：3〜4 日．

### d0010 D2. ネットワークの条件の模擬（levers に入れない．人間の判断 U2）

- コメント：「異なるネットワークで繋がれた環境では」「無線を想定した通信量の評価」．
- 方法案：WAFL-Fast と同じ `tc`/netem で，質問者とノード・委託先の間に遅延（10・50・100 ms），損失（0・1・5%），帯域（10・100 Mbps）を入れる．P2P（往復が多い）と中央（質問者と中央の間の 1 本だけ．最初の集約の転送も含める）で，待ち時間・時間切れ・正答率を比べる．
- 判断が要る理由：共有の機材の root 操作で，他の研究者の通信に影響しうる．

### d0010 D3. 同時の質問が増えたときの PC ごとの負荷と通信量（実機．優先度：中）

- コメント：「複数の質問が同時に発生した場合の，各 PC への負荷や通信量，回答時間」．

- 方法：主構成と中央で，同時の質問の数 {1, 8, 30, 60} を交互に流し（d0009 A6 の手順），各ホストの CPU・GPU の使用率，送受信のバイト数（`/proc/net/dev`），要求の数を 1 秒ごとに記録する．
- 測るもの：PC ごとの負荷の偏り（最大と中央値の比），組織全体の通信量（1 問あたり），回答時間の分布．
- 費用：2 日．

## E. 分析の妥当性

### d0010 E1. 持ち主の姓を含む質問を除いた差（再集計．優先度：高）

- コメント：「26% の質問が持ち主の姓を含む．それを除くと差はどう変わるか」．
- 方法：`header_eval.classify_question` で質問を A（持ち主の姓を含む）・B（A でなく，大文字の語が送受信者の名前の語に一致）・C（どちらでもない）に分け，次を群ごとに出す．
  - test：p0007 の A6 と C1-RRF-CE の差（記述．`results/p0007_a6_live/` と中央の実行）．
  - H：d0009 A3 の P2P 3 回と中央 3 回の差（2 段のブートストラップの区間）．
  - Q：Iteration 41・42 の V2 の両腕（記述．中央の Q の実行が無ければ H だけ）．
- 群ごとに，持ち主の特定（hit@3）と分解（a・b・c）も出す．
- 判定：なし（記述）．「A 群を除いた差」を主の数値として報告書に入れる．
- 費用：半日．

### d0010 E2. 流れの違う構成での代償の分解（再集計．優先度：高）

- コメント：「所有者特定や回答の選択が精度に影響しているのは，特定の P2P フローに依存している可能性」．
- 方法：分解を，流れに依らない形に定義し直す．
  - (a) 持ち主の受信箱が，最終回答を作るために参照した受信箱の集合に入らない．
  - (b) 入っていて，最終回答の根拠が持ち主の受信箱の文脈である．
  - (c) 入っているが，最終回答の根拠が持ち主以外の文脈である．
  - 「根拠」は，owner_answer では選ばれた候補の受信箱，断片返却（B1）では質問者へ渡った 5 通のうち得点が最大の文書の受信箱，とする（事前登録で確定）．
- 対象：p0007 の P4-1（hybrid_probe・B1），A4，A5，A6，F-7，d0009 の R3′（H），V2（Q の両腕）．
- 報告：構成ごとの (a)・(b)・(c) の割合と寄与．どの構成でも (a)+(c) が差の大部分を占めるかを書く．
- 費用：1 日．

### d0010 E3. 公平な中央との差の取り直し（実機．優先度：最高）

- コメント：「中央と分散では，データの配置だけでなく検索の絞り込みや回答の選択の過程も違う．精度差を分散化そのものと区別できるか」．
- 問題：d0009 で P2P に入れた改良（V2 の選択：+0.0076．受信箱の中の文脈 bm25：+0.034．いずれも Q のオフラインの再生）は中央に入れていない．backlog B135 の材料には「bm25 の V2 の H 0.7533 は中央 C の H の平均 0.7284 を上回る（対応の無い比較）」とあるが，公平性の原則を満たさないので，この比較で何も主張しない．
- 中央の対応する改良（C*）の決め方：
  - 中央には候補が 1 つしか無いので，V2（候補の間の選択）は対応する改良が無い．代わりに，中央の文脈の選び方を P2P と同じ範囲の規則から dev で選ぶ：{RRF の上位 50 通の cross-encoder の並べ替え（今の C1-RRF-CE），BM25 の上位 5 通，RRF の上位 5 通，密ベクトルの上位 50 通の並べ替え}．
  - 中央にも「文脈が回答を支えるか」の検証で答えを作り直す手順（検証で「支えない」なら次の文脈の組で答え直す）を入れるかは，P2P の V2 の費用（候補 3 つの検証）と釣り合う範囲で事前登録で決める．
- 実行：`d0009.B3_inbox_context_live` で H3 を作り P2P を流すので，**同じ H3 で C* を実機で流す**（運用ルール 10・11）．`d0009.B3_inbox_context_live` の事前登録で中央の腕が既に入っていれば，それを使い，この項目では C* の選択（dev）だけを足す．
- 判定：P2P 主構成 − C* の差を，2 段のブートストラップの区間（H3．各 3 回の想定）で，非劣性（δ = 0.02）と優越（McNemar．対応あり）で判定する．加えて，oracle（持ち主の受信箱だけ．同じ文脈の規則）を流し，分解（E2 の定義）を出す．
- 報告：「同じ改良を入れた中央」との差を主の数値とし，過去の差（test −0.0235，H −0.0098）を並べて，比べる中央の強さで差が変わることを書く．
- 費用：H3 の実機 3〜4 日（`d0009.B3_inbox_context_live` と共有）．

## F. 閲覧権限とアクセス制御

### d0010 F1. 閲覧権限の観点での露出と，中央の権限の同期の遅れ（オフライン＋小さな実機．優先度：高）

- コメント：「文書ごとに機密度や閲覧してよい人の範囲が異なる．見せてはいけない相手に渡ったかで評価すると，所有者が手元で開示の可否を判断できる分散型ならではの利点が示せる」．
- 背景：企業向けの RAG では，検索の後・生成の前に権限を確かめ，利用者が見てよい文書だけをモデルに渡すことが求められる．中央の索引では各文書の権限を複製して同期し続ける必要があり，同期の遅れが問題になる．
- 権限の設定（評価の場面の設定としてだけ使う．ルーティングの信号には使わない．汎用性の原則）：
  - 各メールの閲覧を許す人 ＝ 送信者と受信者（メールの `Sender:`・`Recipients:` の行から作る．アドレスの表記の揺れの正規化の規則を事前登録で決める）．
  - 質問者のモデル：各質問について，(i) 正解のメールを見る権限のある人，(ii) 権限の無い組織内の人，を種 12 で選ぶ（質問者は 150 人の受信箱の持ち主から選ぶ）．
- 比べる構成：
  - P2P：持ち主のノードが，質問者の身元（認証済みと仮定）と自分の手元の最新の権限で，渡す文書を絞ってから取得・生成する．
  - 中央：索引に権限の情報を持たせ，検索の後に絞る．権限の変更（例：ある期間に受信者から外れる人がいる．権限の一部を取り消す出来事を種で作る）が中央に反映されるまでの遅れ L ∈ {0, 1 分, 1 時間, 1 日} を模擬する．
- 測るもの：
  - 権限の無い相手へ渡った文書の数（質問者・委託先の GPU の PC・中央を区別）．
  - 権限のある質問者の正答率（絞ることで失う精度）．
  - 権限の無い質問者に対して「答えない」ことが正しく起きた割合（B1 の採点と合わせる）．
- 段階：(1) 検索と受け渡しの数はオフライン（既存の索引と frontier-eval の仕組み）で出す．(2) P2P のノードの絞り込みの実装（追加だけの設定キー，例：`experiment.acl_filter`）を入れ，H4 の一部で実機の retrieval_only と生成を 1 回流して，オフラインとの一致を確かめる．
- 判定の骨子：P2P の「権限の無い相手へ渡った文書」が 0 であること（実装の確かめ）と，中央の L に対する漏れの数の曲線．比較は記述が中心．
- 注意：メールの受信者を権限とみなすのは単純化である（転送・共有の範囲は表せない）．このことを限界として書く．
- 費用：3〜4 日．

### d0010 F2. 暗号化と認証の費用（実機．優先度：中）

- コメント：「通信の暗号化やアクセス制御を導入した場合にも有効か」．
- 方法：質問者とノード・委託先の間の HTTP を TLS にし（自己署名の証明書．追加だけの設定キー），要求ごとの認証（署名付きのトークン）を加えた場合と加えない場合を，d0009 A6 の手順（同じ時間帯に交互，parallel 30）で比べる．
- 測るもの：待ち時間（p50・p95），処理量，CPU 使用率の増分．
- 費用：1〜2 日．
