## A. 追加で検証すべきこと

### A1. 質問者を複数にした評価（優先度：高）

- 現状：質問者は受信箱を持たない 1 台に固定した．負荷の測定も，質問者 1 台が同時に 30 問を送り続ける条件である．
- 確かめること：
  - 精度：質問者が変わっても正答率が変わらないか．受信箱を持つ PC が質問する場合に，自分の受信箱を他の PC と同じく問い合わせ先として扱うかを決める必要がある．
  - 負荷：cross-encoder の採点は質問者だけが行うので集中する（採点ありで 0.601 問/秒，なしで 1.014 問/秒）．質問者が複数なら採点は分散するが，問い合わせを受ける側の負荷は増える．どちらが効くかは未検証である．
  - 露出：主構成では質問者 1 台あたり少なくとも 37.6% のメールが渡る．質問者が増えると他人のメールを受け取る PC が増えるので，組織全体の露出は増えると考えられる．
  - 障害：質問者は停止した PC を問い合わせ先から外す仕組みを持たないので（B1），質問者の数だけ待ちが生じないか．
- 報告書の今後の課題には入れていない（質疑で出た論点）．
- 着手：Iteration 23（事前登録は journal の Iteration 23．設計の判断は `.claude/research/backlog.md` の B83）．質問者を wafl-ctrl5 と受信箱を持つ CPU の専門家 2 台（192.168.13.100・192.168.14.100）の 3 台にし，自分の受信箱は他の PC と同じく問い合わせ先とする．判定は新しく分けた質問 H．
- 完了：Iteration 23（2026-11-08．採用）．結果は `results/d0009_a1_multi_requester/`（`verdict.json`・`multi_requester.json`），実行は `results/d0009_a1_{n1_r1,n1_r2,n3_r1,n3_r2,n3_hi,f_n1,f_n3}/` と R3′ の当てはめ `results/d0009_a1_*_R3p/`，記述は `.claude/research/journal.md` の Iteration 23．判定（H の 2,862 問．質問者 1 台と 3 台を 2 回ずつ交互に実機で流した．設定は追加だけのキー `cluster.extra_requesters`）：
  - 精度：検索・候補・選択（R3′ の選んだ番号）は全問で同じ．正答率の差（3 台 − 1 台）は −0.0024 で，95% 区間は −0.0054〜+0.0005．事前登録の同等の幅 ±0.005 には下端がわずかに入らず「決まらない」．差があるとも言えず，非劣性（δ = 0.02）は満たす．実機で選んだ max_score も −0.0028 で同じく決まらない．
  - 質問者を分けると生成の PC に要求が届く順と組が変わり，候補の回答の文字列の一致が 0.99 から 0.89 に下がった．片方だけ正解の問が 1 組あたり 20〜24 問に増えたため区間が広がった（幅 ±0.006 で読み直すと同等．事後の見直しで，判定には使っていない）．
  - 負荷：同時の要求の合計が同じなら処理量は変わらない（比 0.96・1.01）．同時の要求を 3 倍にすると処理量は同じで平均の待ち時間が 2.9 倍になる．採点の分散は実機では測れず（質問者の PC に GPU が無い），推定では質問者 2 台以上で律速が採点から生成へ移る．
  - 露出：組織全体の（PC, 文書）の組は全メールの 0.370 から 0.473 に増え（31 台が質問者なら 0.553），質問者 1 台あたりは 0.161 に減る（1/3 より大きい）．
  - 障害：停止した PC には質問者ごとに別々に当たる．コンテナの停止では待ちは生じず，問はすぐ失敗した（約 300 問の約半分）．B1 の評価に使える．
  - 制約：選択と採点はオフラインの当てはめ（C2），各条件 2 回ずつ．

### A2. 「わからない」を許す指示をやめたことによる作り話の評価（優先度：高）

- 現状：受信箱ごとの回答の生成で「わからない」と答えてよいとする指示をやめると，P2P 構成の正答率は 0.0248 上がった（主構成）．この値は再実行による変動を含む．
- 懸念：資料に答えが無い受信箱（持ち主でない受信箱）も何か答えるので，作り話が増える可能性がある．正答率は「わからない」と誤答をどちらも不正解として数えるので，作り話の増減が見えない．
- 確かめること：
  - 回答を「正解・わからない・誤答」に分けて，指示の有無で集計する．
  - 持ち主でない受信箱の回答に，作り話がどれだけ含まれるかを数える．
  - 最終的に選ばれた回答に作り話が残る割合を見る．選択は質問と候補の文脈だけで決まり回答の文には依らないので，持ち主でない受信箱の作り話は選ばれにくいと推測しているが，確かめていない．
- 報告書の限界（第 7.2 節）にも，スライドの p.25 にも書いていない（質疑で出た論点）．
- 着手：Iteration 21（事前登録は journal の Iteration 21）．
- 完了：Iteration 21（2026-11-06．採用）．結果は `results/d0009_a2_fabrication/`（`verdict.json`・`fabrication.json`・`dev/`・人手での確かめ `manual_check/`），記述は `.claude/research/journal.md` の Iteration 21．判定（p0007 の test 2,939 問．A5＝指示あり・R3 対 A6＝指示なし・R3′）：
  - 持ち主でない受信箱の回答の作り話の割合は 0.157 → 0.361 に増えた（差 +0.205．95% 区間 0.193〜0.216）．
  - 最終的に選ばれた回答の作り話の割合は 0.197 → 0.195 で，再実行の変動の幅（0.02）を超えては変わらない（差 −0.002．−0.015〜+0.010）．候補を一様に選んだ場合（0.298）より 0.103 低く，選択は作り話を避けている．
  - 指示をやめた分の正答率の上がりは，選ばれた回答の「わからない」が減った分（0.051 → 0.031）にあたる．作り話が増えるのは持ち主が候補に入らない問（区分 (a)）に限られる（0.497 → 0.575）．
  - 制約：設計に使った test での記述（C1），選択はオフラインの当てはめ（C2），人手での確かめは agent 1 人で 200 件（一致率 0.93・κ 0.86）．

### A3. 差の信頼区間に再実行の変動を含める（優先度：高）

- 現状：差（−0.0235）の 95% 信頼区間は質問のブートストラップだけで求めた．cross-encoder を加える前の構成を再実行したときの正答率の変化は +0.0078（95% 信頼区間の上端 +0.0173）で，差の一部が変動による可能性がある．
- 確かめること：同じ構成を複数回実行し，変動を含めた区間で非劣性（δ = 0.02）を判定し直す．δ は判定規則を記録した時点の変動の最大値 0.006 の約 3 倍として決めたので，変動の測り直しで δ の根拠も見直す．
- A2 との関係：A2 の指示の有無の比較（選ばれた回答の作り話の差 −0.002，正答率の差 +0.022）は再実行の変動と分けられていない．ここで測った変動で読み直せる．
- 着手：Iteration 22（事前登録は journal の Iteration 22．設計の判断は `.claude/research/backlog.md` の B79）．
- 完了：Iteration 22（2026-11-08．採用）．結果は `results/d0009_a3_rerun_variance/`（`verdict.json`・`rerun_variance.json`・ゲート `g0_g3.json`・`g1/`・`g2.json`・`g-e.json`・`g-j.json`），実行は `results/d0009_a3_{p1,p2,p3,c1,c2,c3}/` と R3′ の当てはめ `results/d0009_a3_p{1,2,3}_R3p/`，記述は `.claude/research/journal.md` の Iteration 22．判定（新しく分けた質問 H．test の受信箱ごとの 21〜40 番目の 2,860 問．P2P-R3′ と C1-RRF-CE を 3 回ずつ交互に実機で流した）：
  - 差は −0.0098 で，再実行の変動を含めた 95% 区間は −0.026〜+0.007（2 段のブートストラップと分散の分解で同じ）．非劣性（δ = 0.02）は満たさず，劣っているとも言えない．
  - 再実行の変動は小さく（同じ構成の正答率の差の最大は P 0.001，中央 0.006），変動を含めても区間の幅は 1 回の実行の区間と同じ（比 0.993）．中央の 1 組だけ McNemar の p = 0.046 で，変動が独立な回答の変化だけとは言い切れない．
  - δ の根拠（変動の最大の 3 倍）を測り直しても δ = 0.02 のまま．
  - test の差（−0.0235）に変動を足した区間は −0.040〜−0.007 で，上端は 0 未満のまま．A2 の正答率の差 +0.022 は今回の変動の最大の 3.7 倍で，変動では説明できない．
  - 以降の d0009 の判定は，H と同じ区間の作り方（journal の Iteration 22 の「区間の作り方」）を使う．2,860 問では区間の半幅が約 0.0165 あるので，非劣性を示すには差が約 −0.0035 より大きい必要がある．
  - 制約：選択と中央の再ランクはオフライン（gpu4）での当てはめ（C2），判定モデルは test の採点と一致率 0.89〜0.91 で，H と test の正答率の水準は比べられない．

### A4. 主構成の露出の全体の算出（優先度：中）

- 現状：主構成の露出 37.6% は，cross-encoder の採点のために質問者へ渡る文書を，保存した文書の識別子から数えた下限である．
- 確かめること：GPU を持たない PC が回答の生成を GPU 搭載 PC に委託するときに送る文書を含めた，全体の露出を求める．

### A5. 新規メールと障害の測定の拡張（優先度：中）

- 新規メール：測ったのは転送の間隔と密ベクトルの追加時間だけである．BM25 を含む構成での索引への追加のコストを測る．
- 障害：中央集約型が 45 秒間停止するという仮定に依存した比較である（中央の積分 22.8 = 再起動後の回答できる割合 0.76 × 30 秒）．別の停止時間でも大小が変わらないかを確かめる．

### A6. 負荷・障害・参加の主構成での再測定（優先度：中）

- 現状：負荷・障害・参加は cross-encoder による選択を加える前の構成で測った．負荷の大小は再実行で逆転し（P2P 0.481〜0.497，中央 0.522〜0.535 問/秒），生成を 10 台に分散した中央集約型は P2P 構成の約 2.4 倍だった．
- 確かめること：主構成で負荷・障害・参加を測り直す．負荷は同じ時間帯に交互に流した条件どうしでしか比べられないので，その手順を守る．

## B. 実装の改善候補

### B1. 停止した PC を問い合わせ先から外す仕組み

- 10 台の処理を強制的に停止させると，回答できる割合は 0.747 から 0.028 まで下がった．
- 停止した PC は生存確認によって 2.01 秒で検出できるので，問い合わせ先から外す仕組みを加えれば，この低下を抑えられる可能性がある．

### B2. cross-encoder の採点を複数の GPU に分ける

- 採点は質問者だけが行うので，生成が速い条件では採点が律速になる（A1 と関連する）．
- 採点のモデルは 8B の生成モデルと同じ 12 GB の GPU に共存できなかった（journal の F-6 の記録）ので，採点を置く GPU の割り当ても合わせて設計する．

### B3. 持ち主の特定と回答の選択の改良（研究の主課題）

- 主構成の差の寄与：持ち主が候補に入らない質問（6.8%）が −0.022，入っているのに持ち主以外の回答を選ぶ質問（6.6%）が −0.016，持ち主の回答を選んだ質問（86.6%）が +0.014．
- 候補の回答のいずれかが正解である質問の割合は 0.7989 で，中央集約型の 0.7976 とほぼ同じである．持ち主が候補に入れば必ずその回答を選ぶ規則でも 0.7840 にとどまるので，回答の選択と持ち主の特定の両方を改良する必要がある．
- 持ち主の特定に使う公開情報を詳しくするほど，公開情報だけから持ち主の PC を推定されやすくなる（top-1 の正解率は重心のみ 0.526，語の統計のみ 0.635，両方 0.726）．改良の際は露出と推定されやすさを同時に測る．
- A2 の結果から：主構成の選ばれた回答の作り話は，持ち主が候補に入らない問で 0.575，持ち主以外の回答を選んだ問で 0.387 と高い（持ち主の回答を選んだ問は 0.151）．中央集約型との正答率の差は作り話ではなく「わからない」として現れる（正解 −0.023，わからない +0.021，作り話 +0.002）．改良の評価では正答率に加えて作り話の割合も `atrium abstain-judge`・`fabrication-eval` で測れる（短い断定の答えを判定モデルが「わからない」にする誤りがあるので，人手での確かめを伴う）．
