## 3. T1：判定の補正の記録（約 1 時間．実機・制御点を使わない）

### 3.1 背景（D4 の目視の結果．2026-10-14 に別のセッションで実施済み）

qwen3:0.6b は，回答の書式の例文 `The answer to the question` を中身なしで返すことがある．判定モデル qwen3:8b は，この**中身の無い回答の約 1 割を正解**としていた（journal「EQ5：RQ-B の判定」の「判定モデルの偽陽性」）．

補正の定義が 2 つあった．

- **狭い補正**：`final_answer` が例文**だけ**の回答を不正解に直す（EQ5 の追記で使用）
- **広い補正**：`final_answer` に例文を**含む**回答をすべて不正解に直す（EQ8 の副指標で使用）

EQ5 の B2（CPU の受信箱 1,940 問）で，例文を含み中身がある回答（513 件）のうち判定モデルが正解とした 213 件から 30 件を無作為に抜き出して（`random.seed(1)`，`results.jsonl` を読んだ順の qid のリストから `random.sample`）目視した．

- 27 件は正解と照らして正しい答えだった（例：`The answer to the question is five business days.`）．
- 残りは，質問の言い直し 1 件，プロンプトをそのまま返したもの 1 件，判断のつかないもの 1 件．

**決定：狭い補正を補正値の定義とする．広い補正は誤り**（正しい答えのほぼすべてを不正解にする）なので使わない．

### 3.2 定義（固定）

- 判定の対象は各行の `final_answer`（`results.jsonl`）．
- 例文だけの回答：`re.fullmatch(r"\s*the answer to the question\s*[.:]?\s*", final_answer, flags=re.IGNORECASE)` に当たるもの．
- 狭い補正の正答率 ＝（判定モデルが正解とした数 − 例文だけの回答で正解とされた数）／ 問の数．判定できなかった出力（`correct` が `None`）は不正解として数える（EQ4 の事前登録と同じ）．
- CPU の受信箱：その実行の `placement.json` で，ホストが `192.168.13.` または `192.168.14.` で始まるノードが持つ `shard_ids`．質問の受信箱は `selected_sources[0]`（routing=oracle なので 1 個）．
- 同じ qid が複数行あるときは最後の行を使う（`read_results` と同じ）．

## 4. T2：持ち主推定の定義の統一（約 2 時間．制御点のコンテナ）

### 4.1 問題

EQ2 の「所有者 top-1」は**メール本文**（長い文）から持ち主を当て，hit@1 は**質問文**（短い文）から正解の受信箱を当てる．入力の情報量が違うので，「公開情報は見つけてもらうことより持ち主を当てることに役立つ」という EQ2 の読み取りには，入力の違いが混ざっている．

### 4.2 測るもの（同じ公開情報・同じ採点の関数で，入力だけを変える）

公開情報を使う 4 方式（card_sim・term_sketch・centroid_sim・multi_centroid．EQ2 で選んだ大きさ）について，次の 3 つの入力で持ち主の top-1 と AUC を出す．

| 入力 | 中身 | 数 |
|---|---|---|
| Q：質問文 | test の質問（EQ2 と同じ 2,940 問）．top-1 は EQ2 の hit@1 と一致するはず | 2,940 |
| E：メール本文 | EQ2 と同じ所有者推定用のメール（受信箱あたり最大 10 通，種 12） | 1,460 |
| E_short：短く切ったメール本文 | E の各メールを，test の質問のトークン数の中央値（arctic-embed-m-v1.5 のトークナイザで数える）に先頭から切ったもの | 1,460 |

- E_short は「同じ長さなら，質問文とメール本文で持ち主の当てやすさは同じか」を見る対照である．
- flood_score・ragroute・random は受信箱ごとの公開情報が無いので，EQ2 と同じく偶然の水準（top-1 1/150，AUC 0.5）とする．

### 4.3 実装

- `src/atrium/owner_eval.py` と CLI `atrium owner-eval --data-dir <> --out-dir <>`．`advert_eval` の `load_inboxes`・`build_methods`・`owner_probes`・`owner_auc`・`bootstrap_ci` を再利用し，**`advert_eval.py` 自体は変えない**（必要なら関数を追加するだけ）．
- 公開情報の大きさは EQ2 で選んだ値（`config.yaml` の `data.enronqa`：card_subjects 40，term_sketch_size 200，n_centroids 32）を使い，選び直さない．
- `scripts/tasks/remote.sh` に `owner_eval` のサブコマンドを足す（既存の `churn_eval` と同じ形．制御点のコンテナで実行し，`results/<run_id>/` に書く）．
- テスト：小さな人工の受信箱で，入力 Q のとき top-1 が `hit_at(ranks, 1)` と一致することと，E_short の切り詰めの長さ．

### 4.4 事前登録（journal に書いて push してから実行）

- 実行は 1 回だけ．結果を見て入力・大きさ・切り詰めの長さを変えない．
- **退行の確認**：入力 Q の top-1 が EQ2 の hit@1 と小数 3 桁で一致すること（card_sim 0.112，term_sketch 0.293，centroid_sim 0.264，multi_centroid 0.349）．入力 E の top-1・AUC が EQ2 の所有者 top-1・AUC と一致すること（0.168/0.760，0.425/0.939，0.284/0.853，0.527/0.950）．一致しなければ判定に進まず §9 の 1 で止まる．
- **H-O1**：4 方式のそれぞれで，E_short の top-1 が Q の top-1 より高いかを，95% ブートストラップ信頼区間で比べる．区間が重ならなければ「同じ長さでも，メール本文の方が持ち主を当てやすい」，重なれば「EQ2 の差は入力の長さで説明できる」と書く．方式ごとに記録する（全体の判定は付けない）．
- 予想（判定に使わない）：term_sketch は送信者の名前などの固有名詞で，短くてもメール本文の方が当てやすい．

### 4.5 手順

1. 実装 → `mise run check` → commit・push．
2. 事前登録を journal に書いて commit・push．
3. イメージを publish し（EQ7a の `eq7a_run.sh` と同じ手順），`bash scripts/tasks/remote.sh owner_eval 20261014_t2_owner_eval` を実行し，`rsync` で `results/20261014_t2_owner_eval/` を取得する．実行スクリプトとログも同じディレクトリに置く．

## 5. T3：150 人での新参者の評価（4〜6 時間．制御点のコンテナ）

### 5.1 問題

E2（MedRAG）の新参者の評価はデータ源が 4 つしかなく，判定の基準も弱かった（journal「E2：LOSO の判定」）．EnronQA の 150 受信箱で，新参者（学習のときにいなかった受信箱）を見つけられるかを測る．公開情報を使う方式と flood_score は学習が要らないので，新参者でも挙動は同じである．比べる中心は**素朴な中央方式（ragroute）の再学習の有無**である．

### 5.2 設計（固定）

- 新参者：150 受信箱から `numpy.random.default_rng(12)` で 30 個を非復元抽出（並びは受信箱名の昇順に並べてから抽出）．選ばれた 30 個を journal に記録する．
- 各新参者 n について：
  - **ragroute-upper**：既存のルーター（150 受信箱すべてで学習済み．`paths.router`）．作り直さない．
  - **ragroute-frozen**：n を除いた 149 受信箱で学習し直したルーター（`train_router(cfg, ..., exclude=[n], out_dir=<作業ディレクトリ>/newcomer/<n>/)`．負例の数・種・ハイパーパラメータは既存のルーターと同じ）．判定時は n の one-hot を 0 にする（`RagrouteRouter(allow_unseen=True)`．E2 の `ragroute-frozen` と同じ）．
  - 学習の要らない方式：card_sim・term_sketch・centroid_sim・multi_centroid（EQ2 で選んだ大きさ）・flood_score（密ベクトル）・random．EQ2 と同じ計算で，n の扱いは変わらない．
- 評価する質問：test のうち正解の受信箱が n である問（受信箱あたり最大 20 問なので最大 600 問）．30 個の新参者の問を合わせて集計する（pooled）．
- m = 2（EQ2 で決まった値）．
- ルーターの作業ファイルは制御点の `/home/denjo/atrium-data/enronqa/newcomer/`（既存の `router/` とは別）に置き，`results/` には評価の値だけを書く．
- **所要時間の上限**：最初の 1 個の学習の時間を測り，30 個の合計が 4 時間を超える見込みなら，新参者を先頭の 15 個に減らす（種と並びは同じ）．この規則も事前登録に書く．

### 5.3 実装

- `src/atrium/newcomer_eval.py` と CLI `atrium newcomer-eval --data-dir <> --out-dir <> [--n-newcomers 30]`．`advert_eval` と `train_router` を再利用し，既存の関数の既定の動作は変えない．
- `scripts/tasks/remote.sh` に `newcomer_eval` を足す．
- テスト：小さな人工データで，除外した受信箱の one-hot が 0 になること，評価する質問が新参者の問だけであること．

### 5.4 事前登録（journal に書いて push してから実行）

- 実行は 1 回だけ．
- **退行の確認**：ragroute-upper と学習の要らない方式について，30 個の新参者の問に限った hit@1・hit@2 を，EQ2 の `metrics.json` の質問ごとの値（あれば）または EQ2 と同じ計算から再現し，一致することを確かめる．一致しなければ §9 の 1 で止まる．
- **H-N1**：新参者の問の pooled hit@2 で，ragroute-frozen < ragroute-upper，かつ 95% ブートストラップ信頼区間が重ならないなら「再学習しない素朴な中央方式は，新参者を見つけにくい」を支持．
- **H-N2**：flood_score と，公開情報を使う方式のうち最良のものの pooled hit@2 が，ragroute-frozen より高い（区間が重ならない）なら「学習の要らない方式は，新参者の発見で再学習しない中央方式に勝る」を支持．
- 書き方の制約（D2）：ragroute は素朴な中央方式なので，「中央方式一般」についての主張はしない．
- 参考（判定に使わない）：新参者ごとの値，新参者の問以外（既存の受信箱の問）での ragroute-frozen の hit@2．
- 限界：公開情報の大きさ（件名 40，T = 200，C = 32）と m = 2 は，新参者を含む dev で選んだ値である．

### 5.5 手順

1. 実装 → `mise run check` → commit・push．
2. 事前登録 → commit・push．

## 6. T4：負荷試験（4〜6 時間．実機 31 台）

### 6.1 問題

flood_score は公開情報なしで最も見つけてもらいやすい（EQ2 hit@1 0.722）が，1 問を全 30 台に問い合わせる．1 問ずつ流すと e2e の中央値は 0.089 秒（EQ7b のゲート）だが，30 問を同時に流すと 92.2 秒だった（EQ3）．同時に流す質問の数に対して，待ち時間と処理量がどう変わるかを，公開情報を使う方式（multi_centroid）と比べて測る．

### 6.2 条件（固定）

- `dataset: enronqa`，`answer_mode: retrieval_only`，`question_limit: 2`（受信箱ごとの先頭 2 問．計 300 問．EQ6・EQ10 と同じ集合）．
- `routing`：flood_score，multi_centroid（m = 2）．
- `experiment.parallel`：1，4，8，16，30．
- 各条件 3 回．計 2 × 5 × 3 = 30 実行．
- 各実行の前に deploy する（`results/20261011_eq8_summary/eq8_chain.sh` と同じ形の連続実行スクリプト `results/20261014_t4_load_summary/t4_chain.sh` を作り，実行の一覧は `t4_specs.txt`）．deploy と judge up の再試行（5 分おきに 3 回まで）も同じにする．
- run_id：`20261014_t4_<routing>_p<parallel>_r<1|2|3>`．
- **再開しない**：待ち時間の測定なので，失敗した問を流し直さない（EQ10 と同じ）．失敗は結果として数える．
- 連続実行の間，制御点で他のコンテナ（T2・T3）を動かさない．

### 6.3 指標

- e2e_s の p50・p95（成功した問），probe_s（flood_score）の p50・p95．
- 処理量：成功した問の数 ÷（最後の問の終了時刻 − 最初の問の開始時刻）．`results.jsonl` の時刻または `run_meta.json` から計算する．どちらにも無ければ，集計スクリプトで `timings` の値から算出できる範囲を記録し，記録の方法を journal に書く．
- 失敗率（`error` のある問の割合）と，エラーの種類（`ReadError` など）．
- 1 問あたりにクエリを受け取ったデバイスの数（`query_recipients`）．

### 6.4 事前登録（journal に書いて push してから実行）

- 判定は EQ6・EQ10 と同じ規則：比べる 2 条件の 3 回の p50（または p95）の幅が重ならないときだけ「差がある」．
- **H-L1**：parallel = 30 で，flood_score の e2e p95 が multi_centroid より大きい（3 回の幅が重ならない）．
- **H-L2**：parallel を 1 から 30 に上げたときの e2e p50 の増加の倍率（3 回の中央値どうしの比）が，flood_score の方が multi_centroid より大きい．
- **H-L3**：処理量が頭打ちになる parallel（処理量が前の段より 10% 以上増えなくなる最小の parallel）が，flood_score の方が小さい．
- 失敗率が 1% を超えた実行があっても止まらない（負荷による破綻は結果である）．ただし 3 回とも同じ条件で失敗率が 10% を超えたら，その parallel より上の条件は飛ばして記録する（p0004 §12 の 4 の代わり．この実験に限る）．
- 予想（判定に使わない）：flood_score は 1 問ごとに 30 台へ probe を送るので，parallel が上がると専門家と質問者の接続の待ち行列で p95 が急に伸び，EQ3 と同じ `ReadError` が出る．
- 限界：有線 LAN・1 種類の質問集合．検索だけで，回答の生成は含まない（回答の生成を含む待ち時間は EQ6・EQ10）．

### 6.5 手順

1. 事前登録 → commit・push．
2. 連続実行のスクリプトを作り，`results/20261014_t4_load_summary/` に置く（実行の途中では commit しない）．
3. `nohup` で連続実行し，終わったら `config.yaml` が元の値に戻っていることを確かめる．
4. 集計スクリプト `t4_summary.py` → `t4_summary.out`．journal に判定と，flood_score の失敗の内訳を書く．
5. スクリプト・ログ・30 実行の結果を commit・push し，`results/README.md` に行を足す．`docs/d0006` の RQ-A の節に負荷の結果を加える．
