用語：

- **データ源（source）**：あるデバイスが保持する文書集合とその検索索引．
- **質問者（requester）**：ユーザの質問を受け付けるデバイス．
- **専門家（expert）**：データ源と LLM を持ち，問い合わせに応じるデバイス．
- **宿る型（local-answer）**：専門家が自分の LLM で回答を生成し，回答文だけを返す方式．
- **断片返却型（snippet-return）**：専門家が検索結果の文書断片を返し，質問者側の LLM が回答を生成する方式（従来の連合 RAG）．

## 1. 要約

**一言で言うと**：組織内の各PCが「自分のデータ＋小さなLLM」を持つ専門家になり，新しいPCが加わっても中央の管理者・中央の学習なしに「誰に聞き，誰が答えるか」を決められる仕組みを作る．評価は先行研究で確立したベンチマーク（MIRAGE，FeB4RAG）で行う．

**背景**：プライバシー上データを外部（クラウド）に出せない組織では，院内・組織内で完結する LLM の需要がある．現状の先行事例は中央 GPU サーバ型である．一方，組織にはGPUを持たない既存PCが大量にある．

**先行研究の空白**：データが複数の保管場所に分かれる状況は「連合 RAG（federated RAG / federated search）」として研究されている．代表的な RAGRoute は，
1. 中央の分類器が問い合わせ先を選び（データ源の集合が変わると再学習が必要），
2. 中央の LLM が回答を生成する（各データ源は文書断片を返すだけ）．

本研究はこの 2 つの前提を外す．

**研究問い**：
- RQ1（誰に聞くか）：新しく加わったデータ源へ，中央での再学習なしに正しく問い合わせを振り分けられるか．
- RQ2（誰が答えるか）：専門家が自分の LLM で答える「宿る型」は，断片を返す従来型と比べて精度・待ち時間・外に出るデータ量の点でどうか．
- RQ3（どう出会い，どこまで広がるか）：50 台以上が参加・離脱する条件で，発見と問い合わせの絞り込みをどう設計するか．

**資源**：ThinkPad L480（Core i5-8250U，16 GB，GPU なし）50 台以上と，RTX 3060（12 GB）搭載 PC 11 台．すべて占有利用可能．同一の有線 LAN．

## 2. 背景

### 2.1 本テーマに至った経緯

本研究は，著者がこれまで取り組んできた 3 つの資産の延長にある．

| 資産 | 内容 | 到達点と限界 |
|---|---|---|
| WAFL-Fast（IEEE WF-IoT 2026 採択） | WAFL のモデル交換を FEC 付き UDP と Fail-Fast で高速化．50 台の実機エミュレーション基盤（WAFL-Testbed）で評価 | 通信時間を 50% 以上削減．ただし対象は MNIST の小型 MLP |
| WAFL-PEFT（github.com/babcs2035/WAFL-PEFT） | WAFL で LLM の LoRA アダプタを P2P 交換．RTX 3060 上で 4-bit QLoRA | Iter27（2026-08-08）で停止．(i) lora_A の初期値がノード毎に異なり，A と B を別々に平均していたためマージの相対誤差が 5 ノードで 0.892，(ii) 同一研究室から IEEE CAI 2026 に WAFL＋LoRA の論文が既出で新規性が失われた，(iii) 評価の最小検出可能差（約 8pt）が文献の効果量（0.5〜3pt）を上回る |
| expert-mesh（github.com/babcs2035/expert-mesh） | 10 台の RTX 3060 に Swallow-8B＋ドメイン LoRA を置き，質問を担当ノードへ振り分ける協調推論 | 教師あり分類器でルーティング top1 約 0.85．Iter111（2026-10-05）で「実行可能なレバーなし」として停止．分類器は全ドメインのラベル付きデータで中央学習しており，新ノードが加わると再学習が必要．LoRA による回答品質の向上は大部分が回答形式の順守によるアーティファクトだった |

これらから得た教訓は 3 つである．
1. **協調学習（重みを混ぜる）から協調推論（専門を分担する）へ移る**．expert-mesh の設計書にも，指導教員との議論でこの転換を行った経緯が記されている．
2. **専門性の源泉に本物の差が必要**．LoRA で作った「専門家」には知識の差がほとんどなかった．本研究では専門性の源泉を「各デバイスが持つ文書（データ）」にする．
3. **評価は確立されたベンチマークで，十分な検出力を確保する**．自作データや少数問の評価で判定が揺れることを避ける．

### 2.2 指導教員の構想（ミーティングメモより）

- AI チップ／デバイスが出会ったときに連携しあえる仕組み．デバイスの種類は本当に多様を想定．出会ってまとまると一つのシステムになる．
- デバイスごとに知識のドメインを分け，「担当のデバイス」が質問に答える．身近なデバイス（ローカル環境）に各専門の LLM が「宿る」イメージ．
- broadcast（発見・同報）の仕組みをどうするか．
- 協調学習からは離れる．
- 評価：正しいデバイスが選ばれるか，回答の品質はどうか．全データをまとめた場合との比較は構造が違うので評価になりにくいかもしれない．ベンチマークから作ることも考える．
- 重複（先行研究との重なり）は気にしなくてよい．興味がわき続けるテーマにしたい．

本研究はこれをほぼそのまま研究の形にしたものである．「宿る」は**各デバイスに専門家が一つずつ住む**という解釈を採る．

### 2.3 社会的背景

- **院内完結の LLM は実在の需要である**．例えば Bonn 大学病院は，A100 80GB × 8 枚を載せた院内サーバ 1 台で，1 万人超の職員向けに患者情報を扱う LLM 基盤を常設サービスとして運用している（arXiv:2604.22768）．つまり先行事例は**中央 GPU サーバ型**である．
- 同論文は「ローカルで動かすだけではデータの安全は保証されない」と明言している．分散させれば攻撃面はむしろ広がるため，本研究でも安全性を主張しすぎないよう注意する．
- 本研究の対象は病院に限らず，**閉じたネットワークに既存PCが大量にある組織**（研究室・自治体・学校など）一般とする．PC は GPU があったりなかったりすると仮定する．病院は応用例の一つとして扱う．
- 本研究が主張したい価値は「中央 GPU サーバを買えない組織でも，データを持ち主の手元から出さずに，既存 PC 群で LLM の恩恵を得られるか」の実現可能性とその代償の定量化である．

## 3. 関連研究と空白

### 3.1 連合 RAG（federated RAG / federated search）

| 文献 | 概要 | 本研究との関係 |
|---|---|---|
| **FeB4RAG**（Wang et al., SIGIR 2024，arXiv:2402.11891，github.com/ielab/FeB4RAG） | 連合検索を RAG の文脈で評価するためのテストコレクション．BEIR の 16 サブコレクションそれぞれに当時最良級の密ベクトル検索器を組み合わせて 16 個の「検索エンジン」とし，チャットボット向けに書き換えた 790 件の情報要求を用意．関連度は LLM で付与し，人手の判定と高い一致を示したと報告 | 評価に用いる（§7.2） |
| **RAGRoute**（Guerraoui et al., EuroMLSys 2025，arXiv:2502.19280，github.com/sacs-epfl/ragroute，MIT ライセンス） | 軽量なニューラルネット分類器が質問ごとに問い合わせるデータ源を選ぶ．MIRAGE・MMLU・FeB4RAG で評価し，問い合わせ数を最大 77.5%，通信量を最大 76.2% 削減．MMLU では全データを 1 か所に集めた場合 43.59% に対し RAGRoute 43.29% と同等の精度 | **主たる比較対象かつ実装の出発点**．中央の分類器と中央の LLM を前提とする |
| **DFAMS**（Yang et al., arXiv:2508.20353） | LLM 内部の活性（Dynamic Information Flow）を使ってデータ源を選ぶ．RAGRoute・RopMura と比較 | 比較対象候補．ただし主要評価データ（Wiki・Med）は LLM で生成した問題であり，本研究の「確立されたデータを使う」方針とは合わない．MIRAGE・MMLU は**フィルタした部分集合**（1,546 問・1,222 問）での評価である点に注意 |
| RopMura（Wu et al., arXiv:2501.07813） | プロトタイプに基づくマルチエージェントのルーティング | 比較対象候補（未精読） |
| C-FedRAG（arXiv:2412.13163） | 機密計算（TEE）で連合 RAG を保護 | 安全性の議論で参照 |
| Flower の FedRAG 例 | サーバがクエリを全クライアントへ配り，返ってきた文書を統合して LLM に渡す | 中央集約型の典型例 |
| 連合 RAG の体系的サーベイ（Chakraborty et al., arXiv:2505.18906） | 評価の枠組みが不足していると指摘 | 位置付けに用いる |

### 3.2 新しいモデルを再学習なしで加える LLM ルーティング

- Router-R1（arXiv:2506.09033）：価格・遅延などの簡単な記述子を手がかりに，未知の LLM へも再学習なしで振り分ける．
- ICL-Router（Wang et al., 2026．サーベイ arXiv:2603.04445 で紹介）：少数の「質問と正否」の組から能力プロファイルを作り，代表質問で評価するだけで新モデルを追加できる．
- GraphRouter，IRT-Router，RouteFM（arXiv:2609.37362）など，未知モデルへの汎化を扱う研究が活発．

**ただし，いずれも中央のルーターが全候補を見渡す前提**であり，対象は「どの LLM に聞くか」である．本研究の対象は「どのデバイス（データ＋LLM）に聞くか」で，中央を置かない点が異なる．

### 3.3 エージェントの自己紹介と発見

- A2A プロトコル（a2a-protocol.org）では，各エージェントが名前・説明・スキル・入出力モード・エンドポイントを記した JSON の **Agent Card** を公開する．標準の置き場所は `https://{domain}/.well-known/agent-card.json`（旧版は `agent.json`）．
- 発見方法として仕様が挙げるのは，(1) well-known URI，(2) キュレーションされたレジストリ，(3) 事前設定．**同じ LAN に現れた見知らぬエージェントを同報で見つける方法（mDNS/DNS-SD 等）は定めていない**．これが指導教員メモの「broadcast をどうするか」に当たる空白である．
- 本研究では自己紹介の書式に Agent Card を流用し，社会実装との接続を確保する．

### 3.4 端末群での分散推論（本研究の主題ではない）

- prima.cpp（ICLR 2026，arXiv:2504.08791）は，CPU/GPU 混在・メモリ不足・Wi-Fi の家庭内端末群で 30〜70B を動かす．1 つの大きなモデルを分割する方向であり，「各デバイスに専門家が一つずつ宿る」本研究とは別系統として位置付ける．

### 3.5 空白のまとめ

| 前提 | RAGRoute 等の既存研究 | 本研究 |
|---|---|---|
| 問い合わせ先を決める主体 | 中央の分類器（データ源が変われば再学習） | 各質問者．新参者は自己紹介等で加わる（RQ1） |
| 回答を生成する主体 | 中央の LLM（データ源は断片を返す） | 担当の専門家が自分の LLM で回答（宿る型）も比較（RQ2） |
| 計算資源 | 高性能サーバ上の別プロセス | GPU なし PC 多数＋GPU PC 少数の実機（RQ2, RQ3） |
| 参加者の変化 | 固定 | 参加・離脱が時間とともに起きる（RQ3） |

## 4. 問題設定と理論

### 4.1 システムモデル

- デバイス集合 $V(t)$（時刻 $t$ に参加しているデバイス．時間とともに変化する）．
- デバイス $i$ は次を持つ．
  - データ源 $D_i$（文書断片の集合）と検索器（埋め込みモデル＋索引）．
  - LLM $M_i$（持たない場合もある）．
  - 計算能力：メモリ帯域 $B_i$（CPU 推論の生成速度を支配），GPU の有無．
  - 自己紹介 $d_i$（Agent Card 形式の説明文・スキル・代表例など）．
- 質問者は質問 $q$ に対して，問い合わせ先の集合 $S \subseteq V(t)$ と回答方式 $m \in \{\text{snippet-return}, \text{local-answer}\}$ を決める．
- 目的：回答の正答率（または検索の再現率）を高く保ちつつ，待ち時間・問い合わせ数・外に出るデータ量を小さくする．

### 4.2 「関連するデータ源」の定義（正解ラベル）

本研究は，正解ラベルの定義を先行研究に合わせる．
- **MIRAGE（RAGRoute の定義）**：全データ源から検索した結果を統合・再ランクした上位 $K$ 件（RAGRoute のコードでは $K=15$）に 1 件以上の断片を出したデータ源を「関連あり」とする．すなわち**検索結果から機械的に作るラベル**であり，人手の判定ではない．RAGRoute のリポジトリにはこのラベルファイルが含まれていないため，再計算が必要である（§12.2）．
- **FeB4RAG**：データ源ごとの関連度ラベル（resource selection 用 qrels）が配布されている．LLM による判定である．

### 4.3 待ち時間のモデル

断片返却型：

$$T_{\text{snip}} = T_{\text{route}} + \max_{i \in S} \left( T^{\text{net}}_i + T^{\text{ret}}_i \right) + T_{\text{rerank}} + T^{\text{prefill}}_{r}(L_{\text{ctx}}) + \frac{n_{\text{out}}}{r_r}$$

宿る型：

$$T_{\text{local}} = T_{\text{route}} + \max_{i \in S} \left( T^{\text{net}}_i + T^{\text{ret}}_i + T^{\text{prefill}}_i(L_i) + \frac{n_{\text{out}}}{r_i} \right) + T_{\text{agg}}$$

ここで $r_i$ はデバイス $i$ の生成速度（tokens/s），$L$ はプロンプト長，$n_{\text{out}}$ は出力トークン数である．

**CPU での生成速度の上限**：デコードはメモリ帯域律速であり，$r_i \lesssim B_i / (\text{モデルの重みのバイト数})$．L480 は DDR4-2400 のデュアルチャネル対応で，両スロットに装着していれば理論帯域は $2400\,\text{MT/s} \times 8\,\text{B} \times 2 = 38.4\,\text{GB/s}$（計算値）．このとき，4-bit 量子化で重み約 0.5 GB の 0.6B 級モデルなら上限は毎秒 70 トークン程度，約 2.5 GB の 4B 級なら 15 トークン程度，約 5 GB の 8B 級なら 8 トークン程度になる（いずれも理論上限であり，実効値はこれより低い）．**1 枚挿しなら上限は半分になる**．

**宿る型の最大の懸念はプレフィル（入力処理）である**．RAG では検索した断片をプロンプトに入れるので，例えば 15 断片 × 約 250 トークンで約 3,750 トークンになる．CPU のプレフィル速度は毎秒数十〜百トークン程度と見込まれ（同世代の i5-8350U で小型モデルの pp512 が約 100 tokens/s という報告がある），**4B 級では 1 回の回答に数十秒〜数分かかる可能性がある**．これは E0 で実測し，断片数 $k$ とモデル規模の選択に反映する（§8）．

### 4.4 外に出るデータ量（露出）のモデル

- 断片返却型：1 回の問い合わせで，各データ源から $k_{\text{ret}}$ 個の原文断片が質問者へ出る．RAGRoute のコードでは $k_{\text{ret}}=50$ 件を取得し，統合後に上位 15 件へ絞る．
- 宿る型：原文断片はデバイスの外に出ず，回答文のみが出る．ただし回答文に原文の内容が含まれうるので，**露出がゼロになるわけではない**．本研究では「デバイス外へ出た原文断片の数」と「回答文と原文断片の重複（例：最長共通部分列の比率）」を併記する．

### 4.5 仮説（反証可能な形）

| ID | 仮説 | 反証条件 |
|---|---|---|
| H1 | 新参データ源への振り分けは，再学習した中央分類器（上限）に対し，自己紹介や代表例だけでも一定の割合まで迫れる | leave-one-source-out で，新参源の関連あり判定の再現率が「全員に聞く」以下，または上限との差が大きく縮まらない |
| H2 | 宿る型は断片返却型より原文の露出を大きく減らせるが，CPU 端末では正答率が下がり待ち時間が延びる | 正答率の差が統計的に検出されない（このときは宿る型の代償がないことになり，むしろ好結果） |
| H3 | GPU PC に重いデータ源や重い検索器を割り当てると，宿る型の待ち時間の悪化を大きく抑えられる | 割り当てを変えても待ち時間の分布がほぼ変わらない |
| H4 | 全員に問い合わせる方式は台数が増えると破綻し，絞り込みが必須になる | 50 台規模でも全員方式の待ち時間・負荷が許容範囲に収まる |
| H5 | 最終的な正答率は中央集約 RAG が最も高い | 分散版が同等以上の正答率を示す |

H5 は「分散版が負ける」ことを予想する仮説である．本研究は分散版の優位を前提にせず，何を失って何を得るかの交換条件を示すことを目的とする．

## 5. 研究問い（詳細）

### RQ1：誰に聞くか — 中央の再学習なしで新参者へ振り分けられるか

- 設定：データ源を 1 つずつ「後から加わった新参者」として学習から除外する（leave-one-source-out, LOSO）．
- 比較する方式：
  1. 再学習した中央分類器（RAGRoute をそのまま再学習．上限）
  2. 全員に聞く（RAGRoute の `all`）
  3. 誰にも聞かない（`none`）・ランダム（`random`）
  4. 自己紹介文（Agent Card の description・skills）の埋め込みとクエリの類似度で選ぶ
  5. 新参者が代表的な文書の要約（例：索引のクラスタ中心）を配り，それとの類似度で選ぶ
  6. 新参者に少数の質問を投げて試す（面接方式．試す問数と精度の関係も測る）
- 指標：データ源選択の再現率・適合率・F1，問い合わせ数，下流の検索再現率．

### RQ2：誰が答えるか — 宿る型 vs 断片返却型

- 比較する方式：
  1. 中央集約 RAG（全データを 1 つの索引に集め，GPU 上の LLM が回答．上限・参照点）
  2. 断片返却型（RAGRoute と同じ．回答は GPU 上の LLM）
  3. 宿る型（担当の専門家が自分の LLM で回答し，回答のみ返す．複数の専門家から回答が来た場合の統合方法も比較）
  4. RAG なし（LLM 単体）
- 指標：正答率，待ち時間（中央値・95 パーセンタイル），デバイス外へ出た原文断片数，通信量．
- 変化させる条件：専門家の LLM の規模（0.6B〜8B），GPU PC の役割，断片数 $k$．

### RQ3：どう出会い，どこまで広がるか

- 発見：同一 LAN 上での同報型の発見（mDNS/DNS-SD 等）と Agent Card の取得．
- 規模：L480 を 10 → 25 → 50 台と増やしたときの待ち時間・負荷．
- 時間変動：参加・離脱のスケジュールを与え，壁時計時間ごとのサービス水準（正答率・待ち時間・失敗率）を測る．
- 絞り込み：全員への問い合わせ（expert-mesh の現行方式）と，能力の要約を事前に交換して候補だけに問い合わせる方式との比較．

## 6. 実験基盤

### 6.1 ハードウェア

| 機材 | 台数 | 仕様（確認済み） | 本研究での役割 |
|---|---|---|---|
| Lenovo ThinkPad L480 | 50 台以上 | Core i5-8250U（4 コア 8 スレッド），メモリ 16 GB（全台同じ装着方法），DDR4-2400 デュアルチャネル対応・2 スロット，GPU なし（UHD 620），有線 Gigabit Ethernet，無線 Intel 8265（802.11ac） | データ源（索引の断片）＋小型 LLM を持つ専門家．質問者 |
| RTX 3060 搭載 PC | 11 台 | VRAM 12 GB | 大きい LLM（8B 級）による回答生成，重い検索器のホスト，中央集約 RAG の基準線，索引の構築 |
| ネットワーク | — | 全台同一の有線 LAN | 有線で実施．無線化は範囲外（§11） |

**索引の容量見積もり（計算値）**．MedRAG の 4 コーパスを MedCPT の 768 次元埋め込みで索引化すると，平坦な索引で次の大きさになる．

| コーパス | 断片数 | fp32 | fp16 | 1 台 6 GB 割当（fp16）で必要な L480 台数 |
|---|---|---|---|---|
| PubMed | 23,898,701 | 73.4 GB | 36.7 GB | 7 台 |
| Wikipedia | 29,913,202 | 91.9 GB | 45.9 GB | 8 台 |
| StatPearls | 約 30.1 万 | 0.9 GB | 0.5 GB | 1 台 |
| Textbooks | 125,847 | 0.4 GB | 0.2 GB | 1 台 |

したがって **MIRAGE の設定だけで L480 が 17 台程度必要**になり，「多数の PC が知識を分担する」状況が設計上自然に生まれる．メモリの残り（約 10 GB）で OS と小型 LLM を動かす．PQ 等の圧縮索引を使えば台数は減らせるが，検索精度が変わるため先行研究との比較性に注意する．

### 6.2 ソフトウェア

| 部品 | 採用するもの | 備考 |
|---|---|---|
| 連合 RAG の実装 | RAGRoute（MIT ライセンス） | コーディネータ・ルーター・データ源・LLM エンジンが別プロセスで，asyncio ベース．LLM は Ollama 経由．データ源の追加は `ragroute/config.py`，独自ルーティングは `ragroute/router/` に置く設計．ただしパスが原著者の NFS に固定されているなど，改修が必要（§12.2） |
| 医療 RAG の部品 | MedRAG ツールキット | MedCPT 等の事前計算済み埋め込みを自動ダウンロードする機能あり（PubMed・Textbooks・Wikipedia．StatPearls は対象外） |
| ベクトル検索 | FAISS | RAGRoute・DFAMS と同じ |
| LLM 実行 | Ollama（llama.cpp） | expert-mesh・RAGRoute と同じ |
| デバイス間通信 | HTTP（expert-mesh の probe/dispatch を流用） | 自己紹介は A2A の Agent Card 形式 |

### 6.3 モデル

- **LLM**：RAGRoute のコードが対応している `llama3.1-8B-instruct`，`qwen3-8B`，`qwen3-0.6B` を基本とし，先行研究との比較性を確保する．L480 上の専門家には 0.6B 級を基本とし，E0 の実測次第で 1.7B〜4B 級も検討する．GPU PC では 8B 級．
- **検索器**：MIRAGE では MedCPT（RAGRoute と同じ）．FeB4RAG ではエンジンごとに指定された検索器を使う（例：nfcorpus は UAE-Large-V1，trec-covid は SGPT-5.8B）．**trec-covid の 5.8B 検索器は L480 の CPU ではクエリ埋め込みが重すぎる可能性が高いため，GPU PC に置く**．

## 7. データセットとベンチマーク

方針：**先行研究で確立したものだけを使う．架空のデータは作らない．**

### 7.1 MIRAGE ＋ MedRAG コーパス（主評価）

- 出典：Xiong et al., "Benchmarking Retrieval-Augmented Generation for Medicine", Findings of ACL 2024（arXiv:2402.13178）．github.com/Teddy-XiongGZ/MIRAGE，github.com/Teddy-XiongGZ/MedRAG．
- 質問：5 つの医療 QA データセットからなる計 7,663 問の選択式問題．内訳は RAGRoute 同梱ファイルで確認済み：MedQA 1,273 問，MedMCQA 4,183 問，PubMedQA* 500 問，BioASQ-Y/N 618 問，MMLU-Med 1,089 問．
- コーパス：PubMed（23.9M 断片），StatPearls（30.1 万断片），Textbooks（12.6 万断片），Wikipedia（29.9M 断片）．Hugging Face で `MedRAG/pubmed` 等として配布．
- データ源の分け方：4 コーパスをそれぞれ 1 データ源とする（RAGRoute と同じ）．本研究ではさらに大きいコーパスを複数台に分割する．
- **注意点**：
  - MIRAGE の質問はモデルが事前学習で知っている知識で答えられる場合が多い．DFAMS の表（Qwen2.5-7B，MIRAGE のフィルタ済み 1,546 問）では，RAG なし 68.05，全集約 RAG 65.78，RAGRoute 69.77 と差が小さく，**全集約 RAG が RAG なしを下回ってもいる**．したがって最終正答率は副指標とし，データ源選択と検索の指標を主指標とする．
  - StatPearls は事前計算済み埋め込みが配布されていないので自前で埋め込む．

### 7.2 FeB4RAG（データ源が多い条件）

- 出典：Wang et al., SIGIR 2024．github.com/ielab/FeB4RAG．
- 中身：790 件の情報要求，16 エンジン（BEIR サブコレクション＋検索器），エンジン単位の関連度ラベル（resource selection 用）と結果統合用のラベル，評価スクリプトが配布されている．
- エンジン一覧（配布 `engines.csv` で確認済み）：nfcorpus，fiqa，arguana，scidocs，scifact，trec-covid，nq，dbpedia-entity，hotpotqa，signal1m，robust04，trec-news，msmarco，fever，climate-fever，webis-touche2020．
- **RAGRoute が使っているのは 13 エンジン**で，signal1m・robust04・trec-news を除いている．この 3 つは BEIR の中でも自由にダウンロードできないコレクションである（理由は RAGRoute 側に明記なし．BEIR の配布条件からの推定）．本研究も公開されている 13 エンジンで行う．
- **注意点**：
  - 関連度は LLM による判定である．論文では人手との一致を確認しているが，人手ラベルではないことを明記する．
  - 配布ラベルを集計すると，1 つの要求に対して**関連ありのエンジンが平均 11.93 個（16 個中）**ある（計算値）．つまり「ほとんどのデータ源が関連している」データセットであり，絞り込みによる削減の余地はもともと小さい（RAGRoute でも 13 個中平均 9.20 個に問い合わせている）．
  - 回答は自由記述であり，正答率ではなくペアワイズ比較などで評価される．

### 7.3 MMLU（先行研究との比較用．主評価にはしない）

- RAGRoute は DPR の Wikipedia 索引を k-means で 10 クラスタに分け，各クラスタを 1 データ源としている．
- **人工的な分割**であり「専門性」とは言いにくい．さらにリポジトリ内で評価用（13 科目）と学習用（8 科目）の MMLU 科目集合が一致しておらず，GitHub の Issue #7 でも論文で使った科目集合について質問が出ている（未回答）．再現性が低いため比較参考にとどめる．

### 7.4 日本語について

- 日本語の**連合 RAG 用**ベンチマークは調査の範囲では見つからなかった．
- 単一コーパスの日本語検索評価としては JQaRA（JAQKET の質問＋Wikipedia，1,667 問，100 候補の再ランク課題）や JaCWIR があるが，データ源の分割は定義されていない．
- 架空の実体についての合成文書で日本語 RAG ベンチマークを作った研究（LREC 2026）もあるが，本研究の「架空のデータを使わない」方針から除外する．
- 結論：主評価は英語の確立ベンチマークで行う．日本語は将来課題とする．

## 8. 実験計画

各実験は「入力 → 手順 → 指標 → 成功条件」の順に記す．

### E0：環境の実測（ゲート，最初の 2 週間）

- 目的：§4.3 の見積もりを実測値に置き換え，以降の設計（モデル規模・断片数・台数）を決める．
- 手順：
  1. `sudo dmidecode -t memory` で全台のメモリ装着（8 GB × 2 か 16 GB × 1 か）を確認する．
  2. `llama-bench` で qwen3-0.6B / 1.7B / 4B / 8B（Q4_K_M）のプレフィル（pp512, pp4096）とデコード（tg128）の tokens/s を測る．
  3. FAISS の平坦索引（fp16，200 万〜300 万ベクトル）で 1 クエリあたりの検索時間を測る．
  4. MedCPT のクエリ埋め込み時間を CPU で測る．
  5. L480 間の RTT とスループットを測る．
  6. L480 のストレージ容量を確認する（コーパスと索引の配置に必要）．
- 成功条件：上記がすべて表にまとまり，RQ2 で使う L480 側のモデル規模と断片数 $k$ を決められること．

### E1：RAGRoute の再現（1〜1.5 か月目）

- 目的：比較の土台を作る．再現できなければ以降の比較は成立しない．
- 手順：RAGRoute を改修して手元で動かし，MIRAGE（4 データ源）と FeB4RAG（13 エンジン）で，`ragroute`・`all`・`random`・`none` の 4 方式を実行する．関連ラベル（上位 15 件への寄与）は再計算する．
- 指標：データ源選択の再現率・F1，問い合わせ数，通信量，正答率（MIRAGE）．
- 成功条件：論文の報告値（問い合わせ数の削減率，再現率）と同程度の値が得られること．差がある場合は原因（ラベル再計算，LLM の違い等）を特定して記録する．

### E2：開集合ルーティング（RQ1，1.5〜2.5 か月目，CPU のみ可）

- 手順：§5 RQ1 の 6 方式を LOSO で比較する．MIRAGE は 4 通り，FeB4RAG は 13 通りの除外を行う．面接方式は試す問数を 1, 3, 5, 10, 20 と変える．
- 指標：新参源についての再現率・適合率，全体の F1，問い合わせ数．
- 成功条件（研究として成立する条件）：少なくとも 1 方式が「全員に聞く」より少ない問い合わせ数で，新参源の再現率を上限（再学習した分類器）の一定割合以上に保てること．閾値は E1 の結果を見て事前登録する．
- 早期成果：この E2 単独で研究会発表の分量になる．

### E3：宿る型 vs 断片返却型（RQ2，3〜6 か月目，実機）

- 手順：L480 群に MedRAG コーパスの索引を分割配置し，小型 LLM を載せる．GPU PC には 8B 級 LLM を置く．§5 RQ2 の 4 方式を，MIRAGE 全 7,663 問（時間が足りなければ層化抽出）で実行する．
- 指標：正答率，待ち時間の分布，デバイス外へ出た原文断片数，回答文と原文の重複率．
- 統計：同一問題に対する方式間の正答率差は McNemar 検定（対応あり）．7,663 問で正答率 65% 付近の場合，独立 2 標本でも最小検出可能差は約 2.2pt（検出力 80%，有意水準 5%，計算値）であり，対応ありならさらに小さい．FeB4RAG（790 件）では約 6.7pt と大きくなるため，結論の強さを区別する．待ち時間はブートストラップで信頼区間を付ける．

### E4：規模と時間変動（RQ3，7〜10 か月目）

- 手順：L480 を 10 → 25 → 50 台と増やす．参加・離脱を時刻表として与える（例：一定時間ごとに一部の台を停止・再参加）．発見方式（同報型 vs 事前設定）と問い合わせ方式（全員 vs 絞り込み）を組み合わせて比較する．
- 指標：壁時計時間ごとの正答率・待ち時間・失敗率，新参者が初めて問い合わせを受けるまでの時間，制御通信量．

### E5（任意）：異種の専門家

- GPU の有無に加え，専門家ごとに LLM の規模や種類が異なる条件で，「遅いが詳しい専門家」と「速いが浅い汎用機」のどちらに聞くべきかを扱う．

## 9. 評価指標と統計の方針

| 種類 | 指標 | 出典・定義 |
|---|---|---|
| データ源選択 | 再現率，適合率，F1，問い合わせ数 | RAGRoute と同じ定義．FeB4RAG は配布の評価スクリプト |
| 検索 | 上位 $k$ 件の再現率 | 統合・再ランク後 |
| 回答 | 正答率（MIRAGE），ペアワイズ比較（FeB4RAG） | MIRAGE は選択肢の厳密一致 |
| システム | 待ち時間（中央値・95 パーセンタイル），通信量，失敗率 | 実測 |
| 露出 | デバイス外へ出た原文断片数，回答と原文の重複率 | 本研究で定義（§4.4） |

統計の原則：
- 方式間の比較は**同一の問題集合で対応ありの検定**（McNemar）を使う．
- 成功条件は実験前に記録し，事後に変えない．
- 実機の待ち時間は外乱を受けるので，各条件を 3 回以上繰り返す．

## 10. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| RAGRoute の再現に時間がかかる（パス固定，ラベル未同梱，MMLU 設定の不整合） | E2 以降が遅れる | MIRAGE と FeB4RAG を優先し，MMLU は後回しまたは除外 |
| L480 のプレフィルが遅く，宿る型が実用にならない | RQ2 の結論が「CPU では無理」で終わる | それ自体を定量的な結果として報告する．断片数・モデル規模・GPU PC の役割を変えた条件で改善の幅を示す |
| MIRAGE で正答率の差が出ない | RQ2 の主張が弱くなる | 主指標をデータ源選択と露出・待ち時間に置く（§7.1） |
| FeB4RAG はほとんどのデータ源が関連しており，絞り込みの効果が出にくい | RQ1 の効果量が小さい | MIRAGE（4 源，大きい源の分割で数を増やせる）を主に，FeB4RAG は多源条件の確認に使う |
| 索引の容量・ダウンロード量が大きい（PubMed＋Wikipedia で fp32 約 165 GB） | 準備に時間がかかる | GPU PC で構築し配布．必要ならコーパスの部分集合で先行実験（ただし先行研究との比較性が下がるので明記） |
| 先行研究との重複 | 新規性が問われる | 指導教員の方針（重複は気にしない）に従いつつ，§3.5 の差分を常に明示する |
| 無線での実証がない | 「出会い」の現実性が弱い | 本計画では有線 LAN と参加・離脱の時刻表で模擬する．無線化（Intel 8265 のアドホック対応は未確認）は将来課題 |
| 露出の評価が単純すぎる | 安全性の主張が弱い | 安全性は主張の中心にしない．露出量の比較にとどめ，攻撃・防御は範囲外と明記 |
