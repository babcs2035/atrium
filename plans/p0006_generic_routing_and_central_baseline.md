## 0. 要点（最初に読む）

1. **方向**：ルーティングの研究を，EnronQA（メール）の性質に依らない**汎用の方式**として進める．メールのヘッダー・アドレス・持ち主の名前などの付属情報に頼る方式は主の候補にしない（§3.2）．方式の優劣は，性質の違う 3 つのデータ（EnronQA・FeB4RAG・MedRAG）で確かめる（P3）．
2. **追加するベースライン**：全データを 1 か所に集約し，同じ LLM（llama3.1:8b）で答える**中央集約ベースライン**を入れる（P1．指導教員の要請）．中央は「競合」ではなく「上限・基準線」として扱う．
3. **参加・離脱（RQ-C）は凍結**する．コード・CLI・結果・journal は**残す**．研究サイクルが選ばないよう，レバーを `frozen_levers` に移す（P0，§9）．
4. **評価の型を統一**する．ルーティングの方式はすべて「1 問あたりの要求数（デバイス単位）・往復の回数・見つけやすさ・露出」の 4 軸で測り，1 つの「フロンティア」の表に 1 点ずつ足す（§6，§7）．
5. **順序**：P0（片付け）→ P1（中央ベースライン）→ P2（汎用のルーティング方式，EnronQA）→ P3（他のデータでの汎用性）→ P4（実機での確認と回答まで）→ P5（統合）．P6（拡張）は人間の判断で始める．P0〜P5 で 3〜4 週間の見込み（未測定の見積もり）．

### 1.2 現状の問題（この計画で解くもの）

- **要求数を大きく減らせる方式がない**．要求数を 4 分の 1 にすると hit@2 が約 0.12 下がる．
- **方式の一部がメールの付属情報に頼っている**．特徴語の要約の成績は，質問に持ち主の姓があるか（A 群）でほぼ決まっていた（A 群 hit@1 0.84，それ以外 約 0.10）．
- **中央集約との比較がない**．
- **評価したデータが実質 1 種類**（EnronQA）．ルーティングの方式を他のデータで確かめていない．
- **研究サイクルが凍結した系列を選び続けていた**．Iteration 15〜19 は参加・離脱の系列だった（レバーが尽きると p0004・d0006 の未着手の項目から選ぶため）．

## 3. 守ること

### 3.1 保全の原則（p0004 §2，p0005 §2 をそのまま適用）

- 既存の `results/` は読み取りのみ．既存の `results.jsonl`・`metrics.json` のフィールドの名前と意味を変えない（追加は可）．
- `config.yaml` の既存キーの削除・改名・意味の変更をしない．新キーは既定値付きで追加する．
- 制御点の `/home/denjo/atrium-data/{medrag,feb4rag,enronqa}` の既存の成果物は変更・削除しない．新しい成果物は新しいサブディレクトリに置く．
- journal・backlog・既存の研究文書は追記のみ．
- 事前登録：判定のある評価は，仮説・判定の規則・閾値を journal に書いて **commit・push してから**実行する．
- 実機の連続実行の途中では commit しない．
- `mise run check` を各 commit の前に通す．既存のテストを削除・弱体化しない．
- 退行ゲート（§3.3）を，ルーターや質問者の経路に触れる変更の後に必ず通す．

### 3.2 汎用性の原則（H1．この計画で新しく加える）

ルーティングの方式（Router と，オフライン評価の方式）は，次を守る．

| 区分 | 規則 |
|---|---|
| 使ってよい信号 | (1) 文書の本文から作る表現（密ベクトルの埋め込み，語の統計，文書の標本），(2) デバイスが自分の検索器で返す得点，(3) デバイスの数・応答の有無などの系の情報 |
| 主の候補にしない信号 | メール固有の付属情報（`Sender:`・`Recipients:` の行，アドレス，持ち主の名前），データセット固有の偏り（質問が持ち主の姓を含むこと） |
| 公開情報の作り方 | EnronQA の公開情報（要約）は**ヘッダーを除いた本文から作る**のを主の条件とする（Iteration 3 の `body-advert-eval` の本文の切り出しを使う）．ヘッダー込みは感度分析としてだけ出す |
| デバイス内の検索器 | 各デバイスの索引・検索器は既定のまま（デバイスの内部の事情であり，ルーティングの方式ではない） |
| 質問の偏りの点検 | EnronQA の主の指標は全問で出し，あわせて「持ち主の姓を含む問（A 群）」を除いた部分集合でも出す．A 群を除くと方式の順位が入れ替わる場合は，その方式を「汎用」と書かない |
| 汎用の判定 | 方式の優位は，§7.3 の規則で 3 つのデータのうち 2 つ以上で保たれたときだけ「汎用」と書く |

**名前の台帳**（送受信者の名前→デバイスの対応表）のような，メールでしか作れない方式は実装しない．必要があっても「メール固有の参考値」と明記した付録にとどめる．

**等価性の確認**：C1 は物理的に 1 台へ集めていないが，同じ埋め込みで全体の上位 5 通を取るので，検索の結果は中央の索引と同じになるはずである．オフラインで 73,772 通（journal 記載の通数）の 1 つの索引を作り，全問の上位 5 通の文書 ID が C1 の実機の結果と一致すること（一致率 ≥ 0.999）を確かめる．一致すれば「C1 は精度の上で中央集約と等価」と書ける．物理的に 1 台へ集めた場合の待ち時間は，ノードが 150 受信箱を持てることを確かめられた場合だけ，記録として測る（判定に使わない）．

**事前登録する仮説**（閾値と規則は rc-researcher が確定する．ここでは向きだけ決める）

- H-P1a：C2 > C1（持ち主が分かることに価値がある）．McNemar の正確検定．
- H-P1b：C1 ≥ C3（中央は，flood_score で 2 受信箱に絞る方式より下回らない）．McNemar．

### P2 汎用のルーティング方式（EnronQA，5〜7 日）

**共通の設定**

- 評価は全てオフラインで，既存の埋め込みと得点（flood_score の各受信箱の最大得点など）から計算する．
- 配置は既存の 30 台（1 台 5 受信箱）を主にする．あわせて「1 受信箱 = 1 デバイス」（N = 150）の模擬で，台数が増えたときの傾向を見る．
- 公開情報はヘッダーを除いた本文から作る（§3.2）．
- 指標は §7 の 4 軸．hit は test で計算し，大きさなどの値は dev で選ぶ．

**P2-0 評価の枠組み（`frontier-eval`）**

- 新しい CLI `atrium frontier-eval --dataset <> --methods <> --out-dir <>` を作る．方式は差し込み式にし，**以後のイテレーションでは方式の追加だけで済む**ようにする（イテレーションごとに CLI を増やした Iteration 15〜19 の形を繰り返さない）．
- 出力は §6.2 の `frontier.json`．
- 退行の確認（R4）：flood_score，multi_centroid，centroid_probe（K ∈ {2, 4, 8, 15, 30, 75}），device_probe（D ∈ {12, 24, 30}）の hit と要求数が，既存の記録と一致すること．

**P2-1 要約の質を上げる（F1）**

- F1a **標本による要約**：各デバイスが自分の文書の埋め込みを S 個（無作為抽出，S ∈ {4, 8, 16, 32, 64}）公開する．質問者はそれを 1 つの小さな索引にして，上位に入った標本の持ち主の数と得点でデバイスを順位づける（ReDDE・CSI 型の資源選択に当たる）．
- F1b **語の統計による要約**：各デバイスが本文の語ごとの文書頻度を，上位 V 語（V ∈ {1,000, 4,000, 16,000}）だけ公開する．質問者は CORI 型の式で順位づける．
- 露出は，公開情報の大きさと，公開情報からの文書の出どころの特定（§7.1）で測る．F1a は公開した埋め込みの数そのものが露出になる．

**P2-2 問ごとに台数を変える（F2）**

- 1 段目の得点の分布から，問ごとに 2 段目で聞くデバイスの数を決める（Rank-S・Taily 型の打ち切り）．規則の候補：上位との得点の差が閾値以内のデバイスだけ，得点の softmax の質量が閾値に達するまで，など．上限 D_max を置く．
- 1 段目は F1 の最良の要約か multi_centroid とする．
- これは凍結した `churn_eval.device_probe_cutoff` と同じ考えだが，**参加・離脱を入れずに**評価する．

**P2-3 階層化（F3．DNS 型）**

- デバイスを g 個のグループに分け，グループの代表がグループ内の要約を束ねる．質問者はまずグループを選び，選んだグループの中のデバイスに聞く．
- グループの作り方：無作為と，要約の類似度による k-means の両方（EnronQA には部署の情報がないため）．
- 要求数と往復の回数（グループ → デバイス → 取得で最大 3 往復）を数える．N = 150 の模擬で，要求数の伸びが平坦な方式（全員に聞く方式）より緩やかになるかを見る．

**P2-4 近傍だけを知る P2P（F4．DRAG 型）**

- 各デバイスは近傍 d 台（d ∈ {3, 5, 8}）の要約だけを持ち，質問を得点の高い近傍へ転送する（貪欲な転送と，DRAG の話題を考慮したランダムウォーク TARW 型の 2 種類）．寿命（TTL）と並列の歩き手の数を振る．
- 「質問者が全員分の要約を持たない」という性質を持つ唯一の族として，要求数・往復の回数（ホップ数）・hit を比べる．
- DRAG の原実装（`simulator.py`）の実行可否が研究室内で確認できたら，同じ規則で突き合わせる（H4）．

**事前登録する仮説（向きと既定の閾値．rc-researcher が確定）**

- H-P2a（主）：§3.2 を守る方式のいずれかが，EnronQA（本文のみの要約，N = 30）で **hit@2 ≥ 0.78 を，要求数 ≤ 16（flood_score の半分）**で達成する．

## 7. 評価の標準

### 7.1 露出の指標（データに依らない形）

- **出どころの特定**：各データ源から，評価に使う問の正解の文書以外を最大 10 件ずつ抜き出し（種 12），公開情報だけで出どころのデータ源を当てさせる．top-1 精度と AUC．EnronQA の「持ち主の特定」はこの特別な場合である．EnronQA ではヘッダーを除いた本文を主の入力にする．
- **質問の露出**：1 問あたり質問（またはその埋め込み）を受け取ったデバイスの数．
- **文書の露出**：デバイスの外に出た文書の数（一度きりの集約と，1 問あたりに分ける）．
- 主張の範囲：代理指標であり，攻撃への耐性や保証は主張しない．

### 7.2 統計

- hit・再現率・出どころの特定は，問の再抽出による 95% ブートストラップ区間（種 12）．
- 正答率の比較は，同じ問の集合での McNemar の正確検定．同じ段階の主の比較の組には Holm の補正をかける．
- 待ち時間は各条件 3 回．3 回の範囲が重ならないときだけ「差がある」．
- 採用の規則：事前登録の閾値を満たし，かつ相対の効果が 5% 以上（Iteration 11〜14 の小さな効果の積み重ねを繰り返さない）．

### 7.3 汎用の判定の規則（P3 で事前登録して使う）

- 各データで，方式を「目標の見つけやすさに届く最小の要求数」（届かない場合はフロンティアの下の面積）で順位づける．
  - 目標：EnronQA は hit@2 0.78．FeB4RAG・MedRAG は全員に聞く方式の再現率の 0.95 倍．
- 方式 X が方式 Y より優れることが，3 つのデータのうち 2 つ以上で成り立ち，残りで逆転の差が区間の外にない場合だけ，「X は Y より汎用的に優れる」と書く．
- EnronQA で A 群を除くと順位が入れ替わる方式は，「汎用」と書かない（§3.2）．
