## 4. 優位の定義と判定

### 4.1 比べる構成

| 構成 | 定義 |
|---|---|
| **中央** | 全 150 受信箱の全メールを wafl-ctrl5 の 1 台に集め，1 つの索引で上位 5 通を取り，同じ台の GPU で回答する（C1 と精度の上で等価） |
| **準集権**（感度分析） | 索引は中央と同じ．生成だけを wafl500〜509 の 10 枚に分ける |
| **P2P** | 各デバイスが自分の受信箱を持ち，hybrid_probe（または A で選んだ Router）で問い合わせ先を選び，A で決めた答え方で回答する |

### 4.2 軸と判定の規則（最初の基準．確認的な判定に使う）

| 軸 | 指標 | P2P が「優位」の条件 |
|---|---|---|
| 精度（A） | test の正答率の差（P2P − 中央） | **非劣性**：差の 95% 信頼区間（対応ありのブートストラップ，10,000 回，種 12）の下端が −δ（δ = 0.02）より上．**優越**：McNemar の正確検定で P2P が有意に高い |
| 露出（B） | 2,940 問で外に出た重複なしの文書数 | 中央の 73,772 通の 50% 未満 |
| 負荷（D） | 生成まで含めた処理量と p95 | parallel 30 で，処理量の 3 回の範囲が中央（1 台）より上で重ならない |
| 追従（C） | 新しいメールが答えに使えるまでの時間と費用 | §6.4 の規則 |
| 障害・参加（E） | 障害時の答えられる割合，新しいデバイスが答えに加わるまでの時間 | §6.5 の規則 |

**総合の判定**：「P2P は中央より優位」と書くのは，**精度で非劣性を満たし，かつ B・C・D・E のうち 3 つ以上で優位**のときだけである．非劣性を満たさない場合は，劣る軸を先に書く（§7）．

**δ の根拠**：同じ条件の流し直しの揺れ（最大 0.006，EQ9）の約 3 倍で，原論文の 8B と 70B の差（72.1% 対 77.1%）の半分未満．**現状の hybrid_probe（差 −0.0198）は区間の下端が −0.02 を下回るので，A で精度を上げなければ非劣性を満たさない見込み**である．

### 4.3 判定の出し方

- 各実験は，判定の規則を journal に書いて push してから実行する（事前登録）．
- 判定は機械的に出し，`results/<run_id>/verdict.json` と journal に書く．

### 4.4 基準の見直しの規則（D2 の「臨機応変」を，結論の信頼性を保ったまま行うため）

1. **結果を見る前の見直し**（その実験の test の評価の前）：自由に行ってよい．理由を journal に書き，事前登録として push してから評価する．
2. **結果を見た後の見直し**：行ってよいが，次の全てを守る．
   - 最初の基準による判定（`verdict_original`）を消さない．
   - 見直した基準による判定を `verdict_revised` として別に出し，「事後の見直し」と明記する．
   - 見直しの理由を，結果とは独立の根拠（測定の揺れ，実装の制約，先行研究の慣例など）で書く．「目標に届かなかったから」は理由にしない．
   - 最終報告では，`verdict_original` を先に書き，`verdict_revised` を並べる．
3. 見直しの全件を backlog に `[auto-decided]` で記録する．

### 6.2 A 精度：持ち主ごとの文脈で答えて統合する

**A1 答え方と統合**．新しい answer_mode `owner_answer`：候補の各受信箱について，その受信箱の上位 5 通だけで 8B が答える．CPU のデバイスの受信箱は，対応づけた GPU に文書を渡して答える（B4 と同じ経路）．候補は Router が選んだ上位 m 受信箱．

| 統合の規則（`answer.aggregate`） | 中身 |
|---|---|
| `max_score`（既存の B4 に相当） | 検索の最高得点の受信箱の回答 |
| `abstain` | 「メールに答えが無ければ UNKNOWN」と答えることを許し，UNKNOWN でない回答のうち得点が最高のもの．全て UNKNOWN なら `max_score` |
| `agree` | 回答どうしの一致（正規化した文字列，または埋め込みの類似度）で票を数え，同票は得点で決める |
| `llm_select` | 質問者の 8B が候補の回答から 1 つを選ぶ（参考．expert-mesh では誤りが多かった） |

- 振るもの：m ∈ {2, 3}，統合の規則 4 種．Router は hybrid_probe（D = 16）を主とし，flood_score と oracle を参照にする．
- 選び方：dev の部分集合（受信箱ごとの先頭 2 問，約 300 問）で全組み合わせを流し，dev の正答率が最大の 1 つを選ぶ（同点は要求数と生成の回数が少ない方）．選んだ 1 つだけを test 2,940 問で流す．
- 費用を併記する：1 問あたりの要求数，生成の回数（m 回），待ち時間．

**A2 デバイス内の検索の改良**（A1 の後）

- 各受信箱の中で，BM25（その受信箱だけの統計）と密ベクトルの上位を RRF（k = 60）で統合する（`retrieval.fusion: rrf`．既定は none）．
- 公平性：中央にも同じ改良（全体の BM25 と密ベクトルの RRF）を入れた C1-RRF を流し，**P2P-RRF 対 C1-RRF** で比べる．
- 先にオフラインで Recall@5 を出し，受信箱の中の Recall@5 が密ベクトルより 0.02 以上高い場合だけ回答まで流す．
- 注意：EnronQA の質問は固有名詞を含みやすく BM25 に有利である（原論文の説明）．効果が EnronQA に寄る可能性を記録する．

**仮説**：H-A1（主）P2P は中央に対して精度で非劣性．H-A2 優越．記述：統合の規則ごとの dev の正答率，m と精度・費用，UNKNOWN の割合．

### 6.3 D 負荷・エネルギー

**中央の実装**：新しい routing `central_local`．質問者が全 73,772 通の 1 つの索引（`central-eval` と同じもの）を持ち，上位 5 通を取って同じ台の GPU で回答する．ノードには問い合わせない．先に C1 と上位 5 通の文書 ID の一致を確かめる（同点を許して ≥ 0.999．D9）．

**条件**（受信箱ごとの先頭 2 問 = 300 問．生成まで含める．3 回ずつ．parallel ∈ {1, 4, 8, 16, 30}）

| 構成 | 生成の GPU |
|---|---|
| 中央（`central_local`＋B1） | wafl-ctrl5 の 1 枚 |
| 準集権（中央の索引＋生成を 10 枚に分ける） | wafl500〜509 |
| P2P（hybrid_probe ＋ A で選んだ答え方） | wafl500〜509（委託） |
| P2P（hybrid_probe ＋ B1） | wafl-ctrl5 の 1 枚（参照） |

- 指標：処理量（問/秒），e2e の p50・p95．判定は「3 回の範囲が重ならないときだけ差がある」．
- **エネルギー（K5．ゲート付き）**：各ホストで，CPU は `/sys/class/powercap/intel-rapl*/energy_uj`，GPU は `nvidia-smi --query-gpu=power.draw` を 1 秒ごとに読み，実行の間の積分から 1 問あたりのエネルギーを出す．先に全ホストで読めるか確かめ，読めなければ（権限など）エネルギーは出さずに記録する．
- 読み方：準集権が P2P と同程度なら，「負荷の優位は分散の構造ではなく GPU の台数による」と書く．P2P の主張は「データを集めずに，既存の GPU に生成を分けられる」こと．

### 6.4 C 新しいメールへの追従（実機で時間を測る）

**方法**：test の正解メールから，種 12 で 10% を「後から届いたメール」に指定し，実験の開始時には索引から外しておく．実験の途中で，それらのメールを届ける．

| 構成 | 届いたメールの扱い |
|---|---|
| P2P | 持ち主のデバイスが，その場で埋め込みを作って索引に足す（CPU のデバイスは CPU で埋め込む） |
| 中央 | 間隔 T ごとに，届いたメールをまとめて中央へ転送し，索引に足す（T は秒で指定．例：0，60，600，∞） |

**測るもの**
1. 新しいメールが届いてから，それについての質問に正しく答えられるようになるまでの時間（P2P と中央の T ごと）．
2. 実測の費用：CPU のデバイスでの 1 通の埋め込みと索引への追加の時間，中央への転送の大きさと時間，中央での追加の時間．
3. 新しいメールについての質問の正答率（T ごと）．

**判定**（事前登録で確定）：P2P の「答えられるまでの時間」の p50 が 1 秒未満で，かつ中央の T ≥ 60 秒の場合より有意に短い．

**注意（懐疑的に）**：中央が T の間に新しいメールを検索できないのは仮定から自明である．価値は (i) **CPU の既存機材で即時の索引が実用的か**の実測と，(ii) 中央がどの T まで P2P に追いつけるかの数値にある．報告ではこの順で書く．

### 6.5 E 障害と参加（D3：分散の優位のアピールに使う）

**E1 障害**
- 中央：中央の索引を持つプロセスを止めると，全問に答えられない．**再起動から答えられる状態に戻るまでの時間**（索引の読み込みを含む）を実測する．冗長化（2 台）の場合の切り替えの時間と，データの複製の費用も記録する．
- P2P：k 台（k ∈ {1, 3, 6, 10}．無作為，種 12）を止めたときの正答率と，止まったデバイスの検出にかかる時間（要求の時間切れ）を測る．
- 止め方は 2 種類を記録する．(a) 既存の `/v1/admin/availability`（`experiment.churn` が必要．`requester_procs = 1`・1 問ずつ順に流す制約がある．再現性が高い），(b) ノードのコンテナを実際に止める（実機の時間切れを含む）．
- 主の指標：P2P が中央の停止中（0）より高いのは自明なので，「**障害の窓の中で答えられた割合の時間積分**」を，中央の再起動の時間を含めた同じ時間の窓で比べる．

**E2 参加（新しいデバイスが加わる）**
- 150 受信箱のうち 15 受信箱（3 台分．種 12）を最初は外しておき，実験の途中で加える．
- P2P：新しいデバイスが公開情報（hybrid の要約）を作って配り，質問者のメンバー表に載るまでの時間．その後，その受信箱についての質問に答えられるまでの時間．要約の作成はそのデバイス（CPU）で行う．
- 中央：新しい受信箱の全メールを中央へ転送し，索引に足すまでの時間と転送量．
- 判定（事前登録で確定）：P2P が「答えられるまでの時間」で中央より短いか，または同等の時間で転送量（データの露出）が小さい．
- 凍結前の知見を使う：参加の通知の遅れが hit を下げる（Iteration 16〜17）．参加の通知は即時（L_join = 0）を主とし，遅れ 10・100 問を感度として記録する．

**範囲**：E は「P2P と中央の比較」に限る．参加・離脱そのものを主題にした系列（通知の方式の改良，補充の変種など）には進まない（p0006 §9 の凍結を維持）．

## 11. 自律で判断してよいこと・してはいけないこと

## 12. 止まる条件（安全上の条件だけ．D7 によりレビューでは止まらない）

次のどれかに当たったら作業を止め，「状況・実行したコマンド・出力の要点・考えられる原因・次の選択肢（記号付き．推奨に `(Recommended)`）」を backlog に `[needs-human]` で書いて終了する．

1. 退行ゲート（R3〜R5）が崩れ，1 回の修正で戻らない．
2. 中央の索引との一致が，同点以外の理由で ≥ 0.999 に届かない（同点だけなら D9 で自動で続ける）．
3. 既存の `results/`・既存の設定キーの意味・既存のデータを変える必要が生じた．
4. データ・成果物の削除，`mise run clean --full` など破壊的な操作が必要になった．
5. 回答文にメール本文が混入した結果を，整形せずに commit しそうになった．
6. `mise run check` が通らず，1 回の修正で解消できない．
7. 制御点・専門家のディスク使用率が 90% を超える．
8. p0003 §6 の 6〜9（同じコマンドの無分析の再試行，push の失敗，秘密情報の疑い，50 MB を超えるファイル）に当たる．
