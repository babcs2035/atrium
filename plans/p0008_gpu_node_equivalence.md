# wafl500〜509 の構成と性能の同等性を検証する計画

RTX 3060（VRAM 12 GB）を搭載する 10 台について，構成の一致，統制した条件での性能，現在の運用条件での持続性能を別々に判定する．この文書は測定と判定の手順を定める計画書である．実機への接続，設定変更，負荷試験はまだ行っていない．

物理的な個体の完全な同一性は証明できないため，確認した属性と負荷の範囲を明記して結論を出す．最終的には，10 台を実験上同じ性能のノードとして扱えるか，分けて扱う必要があるかを判断する．

## 既存の熱による減速の記録を出発点にする

[既存の引き継ぎ文書](../docs/d0009_rinko_handover.md) の Iteration 36 には，wafl500 が約 3 分の負荷で約 10 トークン/秒へ減速し，温度による減速の累計が増えた記録がある．[backlog](../.claude/research/backlog.md) の B123・B134 周辺には wafl505・509 の温度上昇も記録されている．これらは過去の観測であり，現在の故障や原因を確定する材料にはしない．ただし，短い生成が速いだけでは持続性能を保証できないという測定上の根拠にはなる．

既存の [GPU ゲート](../scripts/d0009/b1_gpu_gate.py) は，アイドル状態，減速の状態，短い生成の速度を調べる実装として参照する．40 トークン/秒という既存の通過基準は，今回の同等性の基準には流用しない．[GPU スナップショット](../scripts/d0009/b2_gpu_snapshot.sh) は，温度と減速の累計の取得方法として参照する．

## 1．最初に現状の構成を保存する

対象は wafl500〜509 の全 10 台とし，ホスト名と GPU の UUID の対応を保存する．UUID やシリアル番号は個体の識別に使い，値の違いを構成不一致と判定しない．情報取得は読み取りから始める．取得できない項目は理由とともに「未確認」とする．

| 比較する層 | 取得する項目 | 確認方法の候補 |
|---|---|---|
| GPU の実装 | PCI の device/subsystem ID，revision，製造元・基板型番，VBIOS，総 VRAM，計算能力・SM 数，対応するクロック・電力範囲 | `nvidia-smi -q -x`，`lspci -nnk`，CUDA のデバイス情報，必要時に現物のラベル |
| GPU と CPU の接続 | PCIe の最大／負荷時の世代とレーン幅，接続スロット，NUMA の対応 | `lspci -vv`，`nvidia-smi topo -m`，負荷中の監視 |
| PC 本体 | CPU 型番・コア数，RAM 容量・速度・構成，マザーボード・BIOS，ストレージ型番・接続，NIC とリンク速度 | `lscpu`，`free`，`lsblk`，`ethtool`，許可された範囲の `dmidecode` |
| 実行環境 | OS・カーネル，ドライバー，実際に使う CUDA ランタイム，コンテナとライブラリ，モデルのハッシュ・量子化 | OS 情報，パッケージ情報，イメージ digest，モデル manifest |
| 運用設定 | power limit，クロック設定，CPU governor，CPU／メモリ制限，GPU の共有，常駐処理，画面出力の有無 | GPU 情報，コンテナ設定，プロセスとサービスの一覧 |
| 冷却と給電 | ファンの状態，吸排気と筐体配置，埃，室温・吸気温度，電源型番・配線 | センサーと現物確認．遠隔で分からない項目は未確認とする |

`nvidia-smi` が表示する CUDA のバージョンだけで実行環境が一致したとは判定しない．PCIe は省電力時と負荷時を分ける．GPU のメモリ接合部温度，ECC，ファン回転数などは取得可能な項目だけを使い，非対応を正常値として埋めない．

## 2．現状と条件を揃えた状態の両方を測る

最初の測定群 A は，現在の設定を保存したうえで，測定用の占有時間を設けて実施する．常駐処理や共有の実態は記録し，競合する処理がある時間帯の結果は，同等性を判定する測定に混ぜない．

測定群 B は，コンテナの digest，モデル，入力，乱数 seed，精度，スレッド数，同時要求数，CPU affinity，GPU への全層配置，KV キャッシュの条件を揃える．モデルや入力は事前に各ホストへ配置し，転送・ダウンロード時間を測定から除く．ホスト側のドライバーや電力設定の差が残る場合は，統制できた範囲を明示する．

設定変更を伴う是正は A の保存後に扱う．通常の自動ブーストを使い，クロックを最低の個体に合わせて差を隠さない．GPU の冷却や電力上限は比較対象でもあるため，変更前後の結果を別の測定群として保存する．

## 3．GPU 単体からアプリケーションまで順に測る

| 試験 | 固定する条件 | 主な指標と切り分ける原因 |
|---|---|---|
| GPU の演算 | VRAM 内に収まる固定サイズの行列，同一の演算実装，FP32 と FP16，TF32 の使用条件を明記 | 演算時間・演算量/秒．CPU やネットワークから独立した演算性能 |
| VRAM と PCIe | キャッシュ容量を十分に超える転送，固定サイズ，ホスト側は pinned memory | VRAM 内の実効帯域，CPU→GPU／GPU→CPU の帯域と遅延 |
| VRAM の健全性 | 空き容量から余裕を残した領域へ固定パターンを書いて照合 | 不一致数，確保可能量，CUDA エラー．全領域の無故障保証とはしない |
| PC 本体 | 同じ CPU ベンチと RAM 帯域試験，専用の一時ファイルへの上限付き I/O | CPU・RAM・ディスクによる前処理やモデル読み込みの差 |
| LLM の生成 | 同じモデル digest・量子化，短／長の固定入力，固定生成トークン数，同時要求数 1 と 4 | 入力処理の速度，生成速度，最初のトークンまでの時間，要求の p50/p95，VRAM 最大値 |
| 埋め込み・採点 | atrium で使う同じモデル，固定テキスト長・batch・精度 | 断片/秒，ペア/秒，処理時間，出力の許容誤差 |
| 通信を含む要求 | 同じ制御点から同じ入力を送る．負荷生成側の余力も測る | ローカル API と遠隔 API の差，RTT，転送帯域，再送，要求の待ち行列 |

GPU 内の時間には CUDA イベントを使い，CPU 側の壁時計では完了を同期して測る．メモリ確保と初回コンパイルは定常性能から分ける．モデルの読み込み時間も別に報告する．早期終了で生成長が変わる場合は，共通の生成長で比較できる実装を使うか，生成長ごとに分ける．

LLM の各条件は，1 回の短い試行で済ませず，各ラウンドで最低 100 要求を測る．p95 の精度が足りない場合は未確定とする．出力の照合も行い，CPU への意図しない処理の退避，異なる演算精度，短い出力による見かけの高速化を検出する．

ネットワークは制御点から各ホストへの往復を基本とする．P2P の経路で差が疑われた場合は，全 45 組を両方向に測る．同時の帯域試験で共通のリンクを競合させない．

## 4．反復と持続負荷で温度による差を捉える

短時間の性能試験は，10 台を 1 回ずつ測る組を 1 ラウンドとし，順番を乱数で入れ替えて 10 ラウンド実施する．複数の時間帯に分け，日時，室温，測定順を保存する．各条件の前に最低 3 分のウォームアップを行い，直近 3 分の温度と速度が安定したかを確認する．安定の目安は温度の範囲が 2 °C 以内，1 分ごとの速度が平均の ±3% 以内とし，10 分で満たさなければ定常状態を未確認とする．冷却の待ち時間は集計から除くが，待った時間は残す．

持続負荷は，各ホストで 30 分を 3 回行う．生成と採点を別に測り，開始直後と最後の 10 分の速度，1 分ごとの推移を比較する．単独稼働を基本とし，その後に全 10 台を同時に使う 30 分の試験を行う．同時稼働での室温・吸気温度と，共有ネットワークや給電の条件も記録する．

監視は全試験で 1 秒間隔を基本とし，GPU 温度，使用率，VRAM，SM／メモリのクロック，消費電力，power limit，ファン，減速理由を保存する．CPU 使用率，RAM，I/O，競合プロセスも追跡する．減速の累計は測定前後の差を使い，起動以来の値を個体間でそのまま比べない．Xid などのログは測定区間に対応付ける．

過去に熱による減速があったため，開始前に冷却状態を確認する．本試験では保守的な中止値として GPU 温度 80 °C を用い，メーカーの条件がそれより厳しければ厳しい方に従う．これは故障温度の定義ではない．熱による減速，ファン異常，Xid，計算の照合不一致が起きた場合もそのホストへの負荷を止める．中止を通過や欠測の削除として扱わず，持続試験の未完遂として報告する．原因を解消するまで同じ負荷を繰り返さない．

## 5．「差が検出されない」と「同等」を区別して判定する

次の許容幅は実験上の提案値である．測定開始前に manifest に固定し，結果を見て広げない．

| 判定対象 | 提案する基準 |
|---|---|
| 構成 | GPU の比較属性，PC 本体，ソフトウェア，運用設定ごとに一致／不一致／未確認を列挙する |
| 主指標 | GPU 演算，VRAM 帯域，PCIe 帯域，LLM の入力処理・生成，埋め込み・採点の処理量について，全 45 組の比が 0.95〜1.05 に収まる |
| 遅延 | 同一条件の p95 の全 45 組の比が 0.90〜1.10 に収まる |
| 持続性能 | 末尾 10 分の速度／最初の安定した 5 分の速度が 0.95 以上．末尾 10 分の処理量も全 45 組で主指標と同じ幅を満たす．完遂し，熱による減速と計算エラーがない |
| 運用上の安定性 | Xid，CUDA エラー，出力の照合不一致，意図しない CPU への退避を個別に報告する |

反復の単位は要求や監視の 1 秒ごとの標本ではなく，独立して繰り返したラウンドとする．ラウンド内の対数性能比から，時間帯を揃えた比較を行う．全 45 組と事前に定めた主指標・条件をまとめて覆う，同時 95% 信頼区間を求める．実装を単純にする場合は，比較数に応じた Bonferroni 補正を用いる．区間全体が許容幅に入った項目だけを同等と判定する．

区間が許容幅をまたぐ場合は「未確定」，区間全体が許容幅の外にある場合は「性能差あり」とする．有意差がないだけでは同等としない．10 ラウンドで精度が足りない場合は，ばらつきから必要な反復数を見積もって別の追試を計画し，通過するまで測定を追加する運用を避ける．

10 台すべてを同等と呼ぶには，指定した全条件で主指標・遅延・持続性能の基準を満たす必要がある．中止したホストも 10 台の結果に含め，残った台だけの結論を全体へ広げない．構成の一致と性能の同等性は別々に報告する．

## 6．差が出たら，一度に一要因だけ変えて再測定する

演算自体の差はクロック・電力・温度・演算設定，PCIe だけの差はリンクと CPU／RAM，アプリケーションだけの差はモデル・処理の配置・CPU 制限・待ち行列を順に照合する．単独では揃って同時稼働で崩れる場合は，吸気温度，共有リンク，負荷生成側の飽和を調べる．

冷却，ドライバー，電力設定などを変更した場合は，変更内容と時刻を保存し，影響する試験を変更前後の別系列で繰り返す．GPU と筐体のどちらが原因か遠隔で切り分けられない場合は，現物点検や GPU の入れ替えを追加調査とする．物理作業はこの測定の自動実行には含めない．

## 7．実施順と成果物を固定する

実装時には `scripts/` の既存構成に沿って情報収集・負荷実行・分析を分け，対象，入力，反復数，中止値を専用の測定 manifest に保存する．現在の `config.yaml` と研究サイクルの状態は変更しない．ノードは外部へ接続しないため，必要なイメージと資材は既存の制御点経由で事前配布する．

1. 全台の情報を収集し，構成差と未確認項目を一覧にする．
2. 冷却・占有・監視・中止処理を確認し，代表機の短い試行で測定器を検証する．
3. 全台で現状 A と統制した B の短時間試験を実施する．
4. 各台の持続負荷と全台同時負荷を実施する．中止した機の結果も保存する．
5. 同等性を集計し，差のある項目だけを追試する．

結果は `results/<run_id>/` に manifest，ホスト別の情報，要求ごとの測定値，監視 CSV，中止理由，分析結果を保存する．最終報告には，10 台の構成比較表，性能比と信頼区間，温度・クロック・速度の時系列，現状 A と統制後 B の対比を含める．

完了条件は，全 10 台について「構成」「短時間性能」「持続性能」の判定と根拠が揃い，差の原因について確認済みと未解決を区別できることである．同等と判定できなかった場合も，性能群の分割やホストごとの補正が必要かを判断できれば調査として完了する．

持続試験だけで単独稼働の延べ負荷時間は 10 台 × 2 種類 × 30 分 × 3 回＝30 GPU 時間になる．短時間試験も LLM の条件ごとに 10 台 × 10 ラウンド × 100 要求＝10,000 要求を要する．代表機の試行で 1 要求の時間を測り，条件数，冷却待ち，配布時間を加えて日程を見積もる．並行実行する場合は，同じ室内の熱や共通資源による影響がないかを確認し，単独稼働の結果と分ける．
