## 4. なぜ EnronQA を追加するのか

E1 は「MIRAGE のような公開知識の問題集では，LLM が答えを最初から知っているため，誰に聞くかの価値が正答率に出にくい」ことを示した．これは修論の 1 章（否定的結果）として残す．

この研究の中心的な問い（誰に聞き，誰が答えるか）を測るには，**正しいデバイスに聞かない限り答えられない**評価が要る．EnronQA はこの条件を満たす既存の公開ベンチマークである．

- 103,638 通のメールと 528,304 件の質問・回答の組が，**150 人の受信箱に分かれている**（Ryan et al., arXiv:2505.00263）．
- 文脈なしの正答率は 5% 未満（TriviaQA は 80% 超）．再現率 1 ポイントの向上で正答率が約 0.6 ポイント上がる．
- 受信箱あたりのメール数は平均 491.8，中央値 240.5．メール長の中央値は 1,664 文字．テスト質問は 89,316 件（論文 Table 3）．
- 原論文の最良構成は BM25（全 10 万通に対する Recall@5 が 87.5）．採点は Llama-3.1-70B-Instruct による判定．
- 閉じた組織の個人データという設定が，本研究の想定（組織内の各 PC が持ち主のデータを持つ）と一致する．

### 5.2 本計画が主張する新規性（範囲を限定する）

- **C1**：中央を持たない分散 RAG で，「事前に公開する情報の量」を段階的に変え，**見つけてもらえる度合い・データの露出（公開情報からの所有者特定）・質問の露出・通信量**の四つを，同一の私的データ・同一の実機で測る（調査した範囲で初めて）．
- **C2**：回答方式（誰が答えるか）の効果を，**モデルの大きさの効果から対照条件で切り分けて**実機で比べる．GPU あり・なしが混在する組織に固有の「1 台の GPU PC にだけ委託する」方式を含める．
- **C3**：公開知識のベンチマーク（MIRAGE）と完全分離の私的データ（EnronQA）で，同じ基盤・同じ方式を比べ，前者ではルーティングの価値が測れないことを実測で示す（E1 を活かす）．
- **C4**：すべて実機（CPU 20 台＋GPU 10 台）での待ち時間・負荷の実測を伴う．

**主張しないこと**：暗号的な安全性，差分プライバシーの保証，攻撃への防御．露出は「量」として測るだけにする．

## 6. 研究問いと仮説

### 6.1 RQ-A：見つけてもらうために，PC は自分のデータについて何をどこまで明かすべきか

**比べる方式**（すべて `Router` として実装する）

| 名前（`routing`） | 事前に公開するもの | 照会の流れ |
|---|---|---|
| `all`（既存） | なし | 全受信箱に本照会 |
| `oracle`（新規．上限） | — | 正解の受信箱だけに照会（評価用．実運用では不可能） |
| `flood_score`（新規） | なし | 1 段目：全受信箱に質問を送り，局所的な最高スコアだけ返してもらう → 2 段目：上位 m 個に本照会 |
| `card_sim`（新規） | Agent Card の説明文（既存の `/.well-known` の Agent Card を流用） | 説明文の埋め込みとクエリの類似度で上位 m 個 |
| `term_sketch`（新規） | 受信箱ごとの上位 T 語（TF-IDF） | クエリとの語の重なりで上位 m 個 |
| `centroid_sim`（新規．p0003 の案と共通） | 受信箱の重心ベクトル | 内積で上位 m 個 |
| `multi_centroid`（新規） | k-means の C 個の中心 | 最大内積で上位 m 個 |
| `ragroute`（既存） | 中央に学習データを集める | 中央の MLP（全 150 源．比較用の上限．新参者の評価では再学習なしの版も） |

m・T・C の値は train・dev の質問で選び，テストでは変えない．

**測る量**

- 見つけてもらえる度合い：正解の受信箱の hit@1・hit@3・hit@m，下流の検索再現率．
- データの露出（公開情報からの所有者特定）：§8.5．
- 質問の露出：1 問あたり質問文を受け取ったデバイスの数．
- 通信量：メッセージ数とバイト数，公開情報の大きさ（バイト）．

**仮説**

- H-A1：`flood_score` は公開情報なしで高い hit を得るが，質問の露出は全台になる．
- H-A2：公開情報を増やすほど hit が上がり，同時に所有者特定の精度も上がる（単調な兼ね合い）．反証条件：両者に単調な関係が見られない．
- H-A3：BM25 のスコアは受信箱ごとに IDF が違うため比べられない．`flood_score` は同一の符号化器による密ベクトルのスコアの方が良い．BM25 のスコアを比べられるようにするには文書頻度の統計を共有する必要があり，それ自体が露出になる．

### 6.2 RQ-B：誰が答えるべきか（対照条件つき）

**ルーティングは `oracle` に固定する**（回答方式の効果をルーティングの誤りから切り離すため）．加えて，RQ-A で最良の非オラクル方式でも B1 を 1 回実行する．

| 条件 | 回答する場所 | モデル | デバイスの外に出るもの |
|---|---|---|---|
| B1 断片返却 | 質問者の LLM（wafl-ctrl5 の GPU） | 8B 級（既存の `requester_model`） | 上位 k 通のメール本文 |
| B2 宿る型 | 正解の受信箱を持つ PC | CPU の PC は 0.6B（主）と 1.7B（副），GPU の PC は 8B 級 | 回答文のみ |
| B3 対照 | 質問者 | B2 の CPU 側と同じ小型モデル | 上位 k 通のメール本文 |
| B4 委託 | CPU の PC が，対応づけた GPU の PC 1 台だけに本文を渡して回答させる | 8B 級 | 本文（ただし受け取るのは 1 台） |

- B2 と B3 の差が「誰が答えるか」の効果，B1 と B3 の差が「モデルの大きさ」の効果．
- B4 は GPU のない PC が多い組織での現実的な折衷．CPU 20 台を GPU 10 台（wafl500〜509）に 2 台ずつ固定で対応づける．
- H-B1：同じモデルなら，B2 と B3 の正答率は同等（文脈が同じため）．差が出るとすれば待ち時間と露出．差が出た場合は原因（プロンプト長・切り詰め・打ち切り）を調べて記録する．
- H-B2：B2（CPU の 0.6B）は B1 より正答率が低い．B4 で正答率は B1 に近づき，露出は B1 より小さい．

### 6.3 副次的な観察（主張にはしない）

- 宿る型でも回答文に元のメールの内容が含まれる．回答文と正解メールの最長共通部分列の比率を記録する．

### 6.4 RQ-C（任意．余力があれば）

- 30 台の参加・離脱を時刻表で与えたときの，壁時計時間ごとの hit・正答率・待ち時間．メールの日付のフィールドはないため，メールの時間的な到着は再現しない．

**wafl-ctrl5 の GPU（12 GB）の割り当て**

- 実験中に載るもの：質問者の LLM（8B 級，Q4_K_M で重み約 5 GB）と，クエリ埋め込みのモデル（約 0.5 GB）．MedRAG の s4〜s7 では，wafl-ctrl5 の GPU に 8B と MedCPT（約 1 億パラメータ）が同時に載り，生成は 1 問約 22 秒だった．EnronQA の埋め込みモデルも同程度の大きさで，再ランクも使わないので，同じく載る見込みである．`config.yaml` の注記では「8B と文脈長 16384 で 2 件分の KV キャッシュまでが RTX 3060 に収まる」．埋め込みモデルを足して収まるかは EQ1 の最初に `nvidia-smi` で確かめる．

### 8.6 採点（U3 を反映．70B は使わない）

**主指標**：判定モデル `qwen3:8b`（質問者の llama3.1:8b と別系統にして自己贔屓を避ける）による正誤．プロンプトは EnronQA 論文の付録 B.6 の判定プロンプトに合わせる．wafl-ctrl5＋wafl500〜509 の 11 台で並列に実行する．

**判定モデルの検証（3 段．いずれも評価の前に基準を事前登録して push する）**

1. **データ付属の答えによる検証（必須）**：EnronQA の `alternate_answers` は，データ作成時に原論文の判定モデル（Llama-3.1-70B）が正答と一致すると判定した別解である．`incorrect_answers` は誤答である．テストの抽出集合からそれぞれ 500 件を取り，判定モデルが別解を正，誤答を誤と判定する率を測る．**どちらも 0.95 以上**を合格とする．70B を動かさずに，70B の判定に照らした検証ができる．
2. **より大きいモデルとの一致（必須）**：本実験の実際の出力 300 件（各条件から層化抽出）を，gpu2（RTX 3090，24 GB）に載る範囲で最大の判定モデル（候補：Qwen3-32B の Q4_K_M，重みは約 20 GB の見込み．載らなければ 14B 級）で採点し直し，Cohen の κ を出す．**κ が 0.8 以上**を合格とする．gpu2 が使えないときは wafl-ctrl5（12 GB）で 14B 級を使う．実際に載るかは EQ4 の最初に確かめる．
3. **人手による確認（任意）**：同じ 300 件のうち 100 件をユーザーが判定し，両モデルとの一致を記録する．

**切り替え規則（事前登録）**：1 または 2 が不合格なら，主指標を下の選択式に切り替え，判定モデルの結果は副指標とする．

**補助指標（判定モデル不要）**：`gold_answers` の 1 つと `incorrect_answers` から作る選択式（選択肢の数は V5 で決める）．原論文にない形式なので「派生指標」と明記する．

### 8.7 統計

- 評価用の質問：テストから受信箱あたり最大 20 問を層化抽出（種で固定．V4 で 20 問に満たない受信箱は全問）．約 3,000 問．
- 方式間の正誤の比較は McNemar の正確検定（既存の `atrium compare`）．正答率 60% 付近，3,000 問で独立 2 標本の最小検出可能差は約 3.5 pt（計算値）．対応ありならより小さい．
- hit や所有者特定の精度は，ブートストラップで 95% 信頼区間を付ける．
- 待ち時間：温度 0 で正誤は決定的なので，正答率の実行は各条件 1 回．待ち時間の主張には，300 問の部分集合で各条件 3 回繰り返す．
- 成功条件・判定の合格基準・切り替え規則・除外規則は，評価の前に journal に書き，**評価の前に push する**（p0003 S4 と同じ事前登録の手順）．
